# tools/collector — каркас калектара (G17.01.a, здымкі — G17.01.b, паўзук — G17.02, медыя — G17.03, вікі — G17.04, YouTube — G17.05)

Лакальны інструмент збору сыравіны з сеткі (эпік G17, спецыфікацыя
[`docs/24_web_collection.md`](../../docs/24_web_collection.md)). Версія G17.01.a —
каркас: схема кампаніі (Zod), схема сховішча (`node:sqlite`), цыкл запуску
з запісам прагрэсу ў `run_log`. G17.01.b дадае здымкавы канвеер: старонка,
атрыманая з loader'а, запісваецца на дыск і рэгіструецца ў `raw_records`.
G17.02 дадае паўзук у паркану: http(s)-сіды і знойдзеныя спасылкі ідуць праз
аўдыт-лог паркану ў той самы здымкавы канвеер. G17.05 дадае YouTube-калектар:
субтытры праз `yt-dlp`, транскрыпт па таймкодах, вокладка. Вікі-калектар
(G17.04) — другі сапраўдны сеткавы шлях: кампаніі з блокам `wiki` ідуць праз
MediaWiki API, міма паўзука (гл. «Вікі»).

## Каманды

```sh
node tools/collector/collector.mjs init                          # стварыць схему сховішча
node tools/collector/collector.mjs run --campaign campaigns/gdansk-2026-09.yaml
node tools/collector/collector.mjs status                        # лічбы па сховішчы
```

`--db <шлях>` задае файл базы; па змаўчанні — `tools/collector/runtime/collector.sqlite`
(тэчка ў `.gitignore`). `init` і `run` ствараюць базу пры першым запуску;
`status` чытае існуючую і на адсутным файле адказвае памылкай (код 2).
Непрыдатны `--db` (напрыклад, каталог) — дыягностыка з кодам 2 для любой
каманды. Коды выхаду: `0` — добра, `1` — кампанія не прайшла
валідацыю (дыягностыкі на stderr), `2` — памылка выкліку або файла.

Сховішча — убудаваны `node:sqlite`: для прамога запуску CLI патрэбны Node ≥ 22.13
(у 22.12 з floor'а engines ён яшчэ пад флагам `--experimental-sqlite`; на 24/26
праверана без флага).

## Што робіць `run`

1. Валідуе YAML кампаніі схемай Zod: без `city`, з дрэннымі значэннямі `fence` —
   адмова з дыягностыкай, што называе поле (`campaign.fence.depth: …`).
2. Стварае схему сховішча пры першым запуску: `campaigns`, `raw_records`,
   `links`, `media`, `run_log`. Калонкі `raw_records` — пашпарт са спецыфікацыі
   даслоўна; `topics[]` са спецыфікацыі захоўваецца як JSON-тэкст у калонцы `topics`.
3. Рэгіструе кампанію (ідэнтычнасць — шлях файла кампаніі; паўторны запуск не
   стварае дублікатаў) і кладзе ў `run_log` па кроку на кожны seed і кожны
   YouTube-ідэнтыфікатар.
4. Выконвае крокі да поўнага вычарпання чаргі: `youtube` — рэгіструе абалонку
   запісу (`source_type=youtube`, `rights=research_only` паводле спецыфікацыі),
   `seed` — па схеме URL: `file://` — здымак з дыску (гл. «Здымкі старонак»),
   `http(s)://` — жывы крок паўзуку (гл. «Паўзук»), іншая схема — толькі
   прагрэс; `crawl` — крокі паўзуку, якія паўзук ставіць у чаргу;
   `image` — крокі медыя, якія здымак ставіць у чаргу (гл. «Медыя»).
   Перапынкаваны працэс пакідае крок у стане `running` — наступны запуск
   завяршае яго, а не пачынае нанава (resume, not restart); крок у стане
   `failed` не перазапускаецца. Прыпынак па серыі памылак (гл. «Паўзук»)
   пакідае неапрацаваныя крокі ў стане `pending` — яны і ёсць кропка
   аднаўлення.

## Здымкі старонак (G17.01.b)

**Мяжа без сеткі.** Loader па змаўчанні чытае толькі `file://`-сіды з дыску —
гэта фіксцурная мяжа канвеера: тэсты і дэма ганяюць поўны цыкл без сеткі.
Сід `http(s)://` ідзе ў жывы паўзук (гл. «Паўзук»), сід любой іншай схемы
(`ftp://`…) — крок завершаецца як прагрэс, як у G17.01.a. Адсутны файл,
пусты дакумент, старонка без `<title>` ці без тэксту абзацаў — крок ідзе ў
`failed` з дыягностыкай, якая называе URL і прычыну; ран працягваецца
(правіла «corrupt input → дыягностыка, не крэш»).

**Што з'яўляецца на дыску.** Здымкі жывуць побач з базай:
`<тэчка базы>/snapshots/<першыя 12 знакаў id кампаніі>/<слаг>-<першыя 8
знакаў хэшу URL>/`:

- `snapshot.html` — сапраўдны HTML байт у байт;
- `text.md` — выцягнуты тэкст абзацамі; анкеры застаюцца на месцы як
  `[тэкст](адрас)`, адносныя адрасы resolved ад URL старонкі;
- `metadata.json` — `title`, `published_at`, `author`, `language` (спецыфікацыя
  называе змест — «загаловак, дата публікацыі, аўтар, мова», імёны ключоў —
  нашы; адсутныя метаданыя = `null`);
- `media/` — фота артыкула (G17.03); да media-крокаў тэчка пустая.

Здымок пішацца адзін раз і нколі не перапісваецца: паўторна дастаўленая
старонка таго ж URL прапускаецца цалкам (resume), ачыстка G17.06 стварае
новыя версіі, сыравіну не чапаючы.

**Дэдуплікацыя** — дзве ступені, як у спецыфікацыі («па URL і па хэш тэксту»):

1. `UNIQUE(campaign_id, url)` — тая ж старонка двойчы = адзін запіс;
2. аднолькавы тэкст пад новым адрасам = асобны запіс з тым самым
   `content_hash` (sha256 выцягнутага тэксту на момант здымку — да
   дабаўлення медыя-блокаў; гэта ключ дэдуплікацыі зместу, `text.md` пазней
   дабаўляе фота) і `canonical_url`, што паказвае на кананічны адрас
   арыгінала, — звязваем, а не дублюем.

Абвешчаны `<link rel="canonical">` становіцца `canonical_url` першапісанага
запісу. Дэдуп абмежаваны кампаніяй.

**Парсер v0** — талерантныя рэгэкспы па `<p>`, `<a href>`, `<img src>`,
`<figure>`/`<figcaption>`, `<title>`, `<meta>`, `<link rel=canonical>`.
Паўзук G17.02 выкарыстоўвае той самы выцяг без зменаў — і для гейту
артыкульнасці (лік абзацаў), і праз здымкавы канвеер — таму прачытаная
старонка з сеткі і яе `file://`-фікстура заўсёды даюць аднолькавыя байты
`text.md`. Выцяг вызначаны: той самы HTML заўсёды дае тыя самыя байты,
інакш параўнанне хэшаў страціла б сэнс.

## Паўзук (G17.02)

Сід `http(s)://` і кожная знойдзеная спасылка (`crawl`-крокі ў `run_log`,
глыбіня — у `detail` кроку) праходзяць праз `crawler.mjs`: паркан → аўдыт →
ветлівасць → загрузка → гейт артыкульнасці → здымкавы канвеер G17.01.b
(`processFetchedPage`, без абходных шляхоў).

- **Паркан** (`fence.mjs`) — дакладныя імёны хастоў: хост кожнага сіду плюс
  `fence.extra_domains`. Паддамен — іншы хост; порт не мяжа; URL, які немагчыма
  прачытаць, не дазваляецца (fail closed). Спасылкі па-за парканам аўдытуюцца
  як `denied` і ў чаргу не трапляюць; крок выканаўчы яшчэ раз правярае паркан
  перад загрузкай — парушэнне там азначае пашкоджаны крок, не загрузку.
  Перанакіраванне за паркан ловіцца па выніковым URL: кантэнт выкідваецца,
  парушэнне трапляе ў аўдыт.
- **Аўдыт-лог** — `<snapshots>/<id кампаніі>/fence-audit.jsonl`, радок на
  падзею: `denied` — паркан адмовіў знойдзенай спасылцы, `allowed` — вырашана
  лёс загрузкі (`fetched: true` — байты сапраўды сцягнуты, `false` — URL ужо
  ў бібліятэцы або спроба скончылася памылкай). Серыялізацыя прыбітая даслоўна:
  парадак палёў `url, decision, fetched`, адзін прабел пасля кожнай двукроп'і —
  крытэр пілота «0 старонак з-за паркану» трымаецца як grep па
  `"decision": "denied", "fetched": true` (але ў jq-радок таксама парсуецца).
- **Ветлівасць** — між запытамі да аднаго хоста вытрымліваецца выпадковая
  затрымка з `fence.delay_s` (па змаўчанні [2, 5] с), замер ад пачатку папярэдняга
  запыту.
- **Гейт артыкульнасці** — старонка без тэксту абзацаў або з іх лікам менш за
  `MIN_ARTICLE_PARAGRAPHS` (3) — гэта меню/каталог: крок `done` з нотаткай
  `skipped` у `detail`, без здымку і без далейшага ходу па яго спасылках.
  Нераспазнавальны дакумент (пусты, без `<title>`) — `failed`, як і ў здымкаў.
- **Серыя памылак** — `ERROR_SERIES_LIMIT` (3) запар няўдач загрузкі
  спыняюць ран з дыягностыкай на stderr (`run stopped — error series…`,
  код выхаду ўсё яшчэ 0); неапрацаваныя крокі застаюцца `pending` — наступны
  `run` працягвае з таго месца.
- **Загрузка** — Playwright-браузер (`netfetch.mjs`): ствараецца ляніва на
  першым http(s)-кроку і зачыняецца ў канцы рана; кампаніі толькі з `file://`
  яго ўвогуле не дакранаюць. Патрэбныя каманды пры адсутнасці — у дыягностыцы.
  Неабходнасць браузера: JS-старонкі і сесія лагіну — `browser_user_data_dir`
  у кампаніі (неабавязковы) перазапускае ўласны профіль аўтара, паролі
  інструмент не захоўвае.
- **Межы сеткавага транспарту:** фота па сетцы не сцягваецца — межа loader'а
  медыя засталася `file://`-фікстурай G17.03, таму image-крокі жывога рану
  ідуць у `failed` з іменаванай дыягностыкай, ран працягваецца; асобная задача
  падцягне сеткавы транспарт медыя.

## Медыя (G17.03)

Кожны `<img>` старонкі (у абзацы або ў самастойным `<figure>`, `src` абавязковы)
— асобны крок `run_log` тыпу `image`; парадак крокаў — парадак з'яўлення на
старонке. Крок: загрузка байтаў праз loader → проба памераў з загалоўкаў
кантэйнера (PNG IHDR, GIF, JPEG SOFn; іншае — дыягностыка) → правіла зместу →
файл → радок `media` → markdown у `text.md`.

- **Правіла зместу:** захоўваецца толькі выява з большай старонкай ≥ 150 px
  (`MIN_CONTENT_IMAGE_PX` у `media.mjs`); драбнейшае — гэта іконкі/лічыльнікі,
  крок завяршаецца як `done` з нотаткай у `detail`, файла і радка няма.
- **Імёны файлаў:** `<слаг артыкула>-img-NN.<ext>` — NN гэта нумар з'яўлення
  выявы на старонке, пашырэнне файла бярэцца з пробы фармата
  (`png`/`jpg`/`gif`). Нумар выводзіцца з самога здымка, таму паўторны запуск
  дае тыя самыя імёны (без `-img-1-1`); прапушчаная дробная выява пакідае
  пропуск у нумарацыі — гэта стабільнасць, а не памылка.
- **Радок `media`:** артыкул, нумар блока `text.md`, перад якім стаіць выява,
  `alt`, подпіс (`figcaption` фігуры, інакш `title` выявы), сапраўдны URL,
  файл, sha256 байтаў, памер у пікселях, `rights` (на raw-ступені наследуецца
  ад запісу — для web гэта `research_only`; адасобленне правоў фота — G17.04+),
  дата збору. `UNIQUE(raw_record_id, file)` робіць паўтор крока пустой
  аперацыяй.
- **Markdown:** `![alt](media/файл)` стаіць перад блокам `position`
  (нумар абзаца, перад якім выява стаяла ў крыніцы), подпіс — радок ніжэй
  курсівам. Устаўка ідэнпатэнтная: паўторны крок не дадае другі блок.
- **Адмовы:** недасяжны URL, чужая схема (loader без сеткі serve-іць толькі
  `file://`), пашкоджаныя байты — крок ідзе ў `failed` з дыягностыкай, якая
  называе URL і прычыну; ран працягваецца, ні радка, ні файла, ні
  markdown-най спасылкі не застаецца.

## Вікі (G17.04)

Кампаніі з блокам `wiki` збіраюцца праз MediaWiki API — міма паўзука, па
асаблівых дзвярах вікі-руху:

```yaml
wiki:
  api: https://pl.wikipedia.org/w/api.php   # поўны адрас api.php
  articles: [Gdańsk, Stocznia Gdańska]
  categories: [Category:Architektura Gdańska]
  depth: 2                                   # узроўні разгортвання катэгорый
```

- **Транспарт.** `api` — гэта мяжа `loadApi`: па змаўчанні сапраўдны http(s)
  fetch да MediaWiki (жывыя прагоны — уручную), у тэстах — запісаныя фікстуры
  праз ін'екцыю, ніводны тэст не ходзіць у сетку. Іншая схема (`ftp://…`) —
  крок ідзе ў `failed` з дыягностыкай «no transport (http/https only)».
- **Крокі.** Кожны артыкул — крок `wiki-article`, кожная катэгорыя — крок
  `wiki-category` з працоўным загадам (`api`, глыбіня) у `detail`. Катэгорыя
  адным крокам запытвае спіс членаў (`cmlimit=max`); артыкулы ідуць у чаргу
  як крокі артыкулаў, падкатэгорыі — як крокі катэгорый наступнага ўзроўню.
  Працяг парцыянавання (`continue`) — нотатка ў `detail`, не маўклівое
  абрэзанне; адна партыя на крок у G17.04.
- **Тэматычны фільтр і глыбіня.** Падкатэгорыя разгортваецца, толькі калі
  яе назва ўтрымлівае адну з тэм кампаніі (`topics`, рэгістр не мае значэння,
  прэфікс `Category:` ігнаруецца), і толькі ў межах `depth` (1 — толькі
  пералічаныя катэгорыі, 2 — плюс іх тэматычныя падкатэгорыі). Пералічаная ў
  канфігу катэгорыя фільтр абыходзіць — аператар выбраў яе сам. Прычына
  адмовы гучыць у нотатцы кроку: «no campaign topic matches (topics: …)» /
  «depth limit N reached».
- **Пашпарт і атрыбуцыя.** `raw_records` атрымлівае `source_type=wiki` і
  `rights=licensed` праз `WIKI_RIGHTS` у `wiki.mjs` (спец: «Вікіпедыя і
  MediaWiki-сайты — licensed (CC BY-SA): цытата дазволена з атрыбуцыяй»).
  `metadata.json` здымка дадае `attribution`: `site`, `revision_id`,
  `contributors_url` (гісторыя рэвізій праз index.php побач з api.php) і
  `license` (`CC BY-SA`, канстанта `WIKI_LICENSE`); `published_at`/`author` —
  час і аўтар рэвізіі. Адсутныя метаданыя — `null` (мовы ў адказе parse няма).
- **Здымкі.** HTML артыкула (фрагмент `parse.text`) агорнуты ў дакумент з
  `<title>` з нармалізаванай назвы і гоне праз той самы здымкавы канвеер,
  што і seed-старонкі: `snapshot.html`, `text.md`, спасылкі ў `links`,
  дэдуплікацыя па URL і хэшы тэксту (два напісанні адной назвы — адзін
  запіс). Медыя-крокі для вікі не ставяцца — фота па-за абсягам G17.04,
  `media/` застаецца пустой тэчкай.
- **Адмовы.** Адсутная назва (error-канверт `missingtitle`), пашкоджаны JSON,
  адказ без `parse.text`/`revisions` — крок ідзе ў `failed` з дыягностыкай,
  якая называе назву і прычыну; ран працягваецца.

## YouTube (G17.05)

Кожны ідэнтыфікатар відэа з кампаніі — крок `youtube` у `run_log`: абалонка
запісу (`source_type=youtube`, `rights=research_only`) рэгіструецца адразу
(G17.01.a), потым канвеер `youtube.mjs` спампоўвае субтытры праз `yt-dlp` і
запаўняе запіс. Выклік — дзве фазы, каб выбар дарожкі жыў тут, а не ў
`yt-dlp`: спачатку `--dump-json` (метаданыя + даступныя мовы), потым другі
выклік піше адзін выбраны VTT (`--sub-langs <мова>`).

**Выбар дарожкі** — адзіная кропка `pickLanguage`: ручныя субтытры
(`subtitles`) маюць прыярытэт над аўтаматычнымі (`automatic_captions`,
якасць); унутры тыпу першая — родная мова відэа, астатнія па алфавіце. Тып і
мова запісваюцца ў метаданыя і ў нотатку кроку.

**Што з'яўляецца на дыску** — `<snapshots>/<id кампаніі>/<слаг>-<хэш URL>/`:

- `transcript.md` — транскрыпт абзацамі: адзін абзац на цьюб VTT з анкерам
  `[ГГ:ХХ:СС]` (секундная дакладнасць); убудаваныя тэгі знятыя, шматрадковыя
  цьюбы склееныя, паўторы rolling-аўтасубтытраў згортваюцца;
- `subtitles.vtt` — сапраўдны VTT выбранай дарожкі;
- `metadata.json` — `title`, `channel`, `upload_date`, `duration_s`,
  `language`, `subtitle_kind`, `subtitle_language`, `cover`;
- `media/<слаг>-cover.<ext>` — мініяцюра-вокладка, правіла імёнаў як у
  G17.03.

Радок `raw_records` запаўняецца `content_hash` (хэш транскрыпта),
`snapshot_path`, `media_dir` праз `fillYoutubeRecord` (upsert абалонкі
застаецца DO NOTHING — двухфазны кантракт).

- **Відэа без субтытраў** — радок у `asr-backlog.jsonl` у тэчцы кампаніі
  (video_id, url, прычына, дата); крок завяршаецца `done` з нотаткай
  `asr-backlog`, ран працягваецца; ніякіх здымкаў за ім.
- **Бінарнік адсутны** — іменаваная дыягностыка (`binary not found — install
  yt-dlp…`), крок `failed`, ніякіх часовых файлаў, чарга крокаў не
  зачапленая; жывы запуск — уручную, як і паўзук.
- **Межа бінарніка** — `createYoutubeFetch({ command })`: каманда па
  змаўчанні `yt-dlp` з PATH; тэсты спаўняюць стаб той самай машынай выкліку
  (сапраўдны spawn, сапраўдны парсінг stdout), сеткі не мае.
