## Acceptance

1. [ ] Every event named in 09 §10, 09 §20 (`guide_nearby_*`) and 21 §7 (`discovery_offer_*`) has exactly one row: required and optional fields, context (app / guide / session / story) and the source anchor it was copied from. The table introduces no names of its own.
2. [ ] Common fields are exactly `event_id`, `type`, `at` and the schema version. `session_id/route_id/version/locale/tier` appear only on events that have that context; a negative fixture (`app_open` or a pre-Start purchase event with an invented `session_id`) is rejected.
3. [ ] `stop_reached` is defined only for pipeline-confirmed presence; `story_play_started` carries `trigger: gps|manual`; a fixture pair shows that a manual play produces no `stop_reached`.
4. [ ] Join rules through `attempt_id`/`offer_id`/`download_id` to a later `session_started` are stated; a chain fixture preview → purchase → download → Start has no session before Start.
5. [ ] Closed reason lists exist for `story_play_failed`, `download_failed`, `purchase_failed`, `autotriggers_unavailable` and `session_ended.reason`; a fixture with an unknown reason is rejected.
6. [ ] Forbidden content, one isolated negative fixture per class: coordinates or exact distances, free text, URLs or tokens, a feedback rating (21 §6: feedback is not an event).
7. [ ] Each row states that local recording does not depend on consent while sending is consent-gated, and that progress never depends on an event.
8. [ ] The discovery payload is exactly `{discovery_revision, offer_id, kind, content_locale, surface}` plus an optional time bucket; `guide_nearby_*` fields follow 09 §20, with R07 limits marked as owned by G07.04.
9. [ ] The fixture test is enumerated by `npm test`; each negative fixture names its single violation ([implementation-rules §14](../../agent-rules/implementation-rules.md)).
