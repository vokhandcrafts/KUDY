# G09.05 — Crash reporting і бяспечная remote config

**Issue:** [#295](https://github.com/vokhandcrafts/KUDY/issues/295) · **Галінка:** `zcode/295` · **Статус:** `complete` (кліенцкае ядро crash-звітаў і remote config даказаныя тэстамі і дэмай; Deno-wiring `GET /v1/config` і Supabase-рантайм — `not-run` па прэцэдэнце G08.01/G09.02: праект Supabase да рэпы не падключаны; усе крытэрыі issue — кліенцкія)

## Што зроблена

Дзве незалежныя рэчы адной лініі «прылада бачыць збой і канфігурацыю — і нічога больш».

**Crash reporting** — `services/crash.ts`: закрытая форма звіта (`crash_id`,
`at`, `schema_version`, `kind`, `fingerprint`), асобная згода
`crash_consent` у durable `settings` (закрыты слоўнік `granted | revoked`,
адсутнасць = «не пыталі»), гейтоўны `submitCrashReport` і інжэктаваны
sink-порт. **Remote config** — `services/remote-config.ts`: fetch →
кантрактная валідацыя → кэш у `settings` → адказ; ланцуг fallback
сетка → кэш → дэфолт з named-дыягностыкамі; кантрактны бок —
`contracts/config/remote-config.mjs` (checker па патэрне hints) +
`remote-config.defaults.v1.json` (бяспечны дэфолт) + схема
`contracts/schemas/remote-config.schema.json` + тыпавы `remote-config.d.mts`.

Уласнік стану: згода crash і кэш канфігурацыі — гэта радкі `settings`
(зона B, SQL у `services/db`, ADR G01.03 §3.3); форма звіта — `services/crash.ts`
(сыравы тэкст не пакідае модуль); дакумент канфігурацыі — кантракт
`contracts/config` (адзіная крыніца палёў і дэфолтаў). Сервернага эндпоінта
crash-звітаў у закрытым спісе API (`09` §5) няма — прызначэнне задаецца
sink-портам; знешні Sentry-клас сэрвіс кампануецца за ім пры наяўнасці
акаўнта (пазнака ў issue). Другой чаргі crash-звітаў не ўводзіцца (прэцэдэнт
G09.02): звіт будуецца і адпраўляецца аднойчы, лёс skipped/failed —
дыспазіцыя выклікача.

### Рашэнне праектавання (arch-plan, кароткі запіс)

```text
owner (crash):  services/crash.ts — згода + закрытая форма звіта + гейт
owner (config): services/remote-config.ts — fetch → validate → кэш → fallback
command path:   збой → buildCrashReport (скрабінг структурай) →
                submitCrashReport (згода з settings) → sink;
                refreshRemoteConfig → GET /v1/config (без auth) → checker →
                кэш settings → readRemoteConfig офлайн
derived views:  няма (ні другога кэша, ні другой чаргі; fingerprint = хэш
                нармалізаванага паведамлення праз інжэктаваны digest)
ordering/idempotency: crash_id генеруе кліент; кэш заменяецца толькі
                прынятым дакументам; згода чытаецца durable перад кожным submit
spec/tests:     issue #295; contracts/config/remote-config.test.mjs;
                services/crash.test.ts; services/remote-config.test.ts
```

## Крытэрый 1 — звіт не нясе сакрэтаў, кантэнту і каардынатаў

- Скрабінг структурай, не фільтрам: outgoing-форма закрытая, сыравы тэкст
  (`message`) спыняецца ў `buildCrashReport` — вонкі ідзе толькі `fingerprint`
  (інжэктаваны digest над абрэзаным паведамленнем). Тэст саджае ў сыравіну
  сінтэтычны сакрэт, назву кропкі і каардынаты і правярае ніводнага
  падрадка ў звіце + закрыты набор ключоў (`crash.test.ts`, крытэрый 1 ×2:
  скрабінг + fingerprint-дэдуп без зместу).
- Невядомы `kind` — іменаваная памылка выклікача `invalid_crash_kind`:
  прыдуманага класу збою не бывае.

## Крытэрый 2 — згода crash яўная і асобная ад аналітыкі

- Уласны ключ `crash_consent` (той самы закрыты слоўнік, што ў аналітыкі;
  адсутнасць = гейт закрыты). Крыжаваныя тэсты абодвух кірункаў:
  `analytics_consent: granted` не адчыняе crash-гейт (нуль выклікаў sink-а),
  `crash_consent: granted` не адчыняе `flushAnalytics` (нуль адпрацовак пры
  жывой чарзе); кожнае рашэнне піша толькі свой радок `settings`
  (`crash.test.ts`, крытэрый 2 ×3).
- Параўнанне з пашкоджаным радком — іменаваная дыягностыка
  `invalid_consent_state`, не цішая «закрыта».

## Крытэрый 3 — канфігурацыя валідуецца схемай; крывы адказ → дэфолт, не краш

- Палі дакумента — даслоўна радок `GET /v1/config` з `09` §5:
  `trigger_radius_default`, `dwell_ms`, `accuracy_gate_m`,
  `moment_cooldown_min`, `moments_per_session_max`, `min_app_version` +
  канверт `config_schema_version` (прэцэдэнт `catalog_schema_version`,
  contracts README). Слоўнік закрыты, абедзве мяжы кожнага дыяпазону.
  Named-правілы checker-а: `config-unknown-field`, `config-field-required`,
  `config-field-type`, `config-value-below-minimum`,
  `config-value-above-maximum`, `config-version-unsupported`,
  `config-value-non-finite` (гард NaN/Infinity, #391 ідыёма),
  `config-accuracy-exceeds-radius` (напрамак `11` §13: accuracy ≤ radius).
  Па адным ізалюючым негатыве на кожнае правіла + карумпаваныя ўводы
  (null, масіў, радок, лік) адказваюць дыягностыкамі, не throw
  (`remote-config.test.mjs`).
- Сэрвісны ланцуг: 200 + валідны → кэш і адказ; крывы/не-200/сетачная
  памылка/непарсавальнае цела → named-дыягностыка + fallback, `refresh` не
  кідае выключэнняў для дадзеных (`remote-config.test.ts`, крытэрый 3 ×5).

## Крытэрый 4 — кэш офлайн; канфігурацыя не адчыняе платнае і не ломіць правілы

- Кэш — радок `settings` (`remote_config_cache`): апошні прыняты сеткавы
  дакумент; заменяецца толькі наступным прынятым — адхілены адказ ніколі не
  перазапісвае кэш. `readRemoteConfig` працуе без сеткі; крывы кэш (не JSON
  або па-за кантрактам) — не давераны і не «рамантаваны» тут:
  `config-cache-corrupt` / `config-cache-invalid` + дэфолт.
- Структурная немагчымасць разблакоўкі: схема несе толькі шэсць лічбаў з
  закрытым слоўнікам — поля разблакоўкі/URL/вольнага тэксту ў дакумента
  існаваць не можа (тэсты: `unlock_extended` → `config-unknown-field`;
  URL-радок у поле → `config-field-type`); верхнія мяжы дыяпазонаў не
  дазваляюць варожаму дакументу знесіліць брамы сесіі (межы — палітыка
  валідатара, пазначаная ў description схемы).

## Свядомыя рашэнні і межы доказу

- **`services/consent.ts` — агульны accessor слоўніка згоды.** jscpd-парог 0:
  другі варыянт чытання `granted|revoked` + дыягностыкі быў бы клонам. Accessor прымае фабрыку памылкі: закрыты клас памылак кожнага ўласніка не змяніўся (тэсты analytics зялёныя бяз правак).
- **`services/config.ts` (G07.05) не расшыраецца; канон `19` амэндаваны.** Радок
  `19` §2.3 называў уладальнікам remote config `services/config.ts`, але яго
  загаловак фіксуе адзінства з G07.05 — гэта node-side загрузчык bundle-лічбаў
  (імпартуе node:fs, у RN-бандл не трапляе, а remote-config павінен;
  прэцэдэнт адхілення — results G09.02). Па implementation-rules 6 гэты PR
  свядома амэндуе `19` §2.1/§2.3/§3: уладальнік remote config —
  `services/remote-config.ts`.
- **Правадка ў дадатак — `not-run`.** У `refresh`/`submit` пакуль няма
  выклікача (прэцэдэнт `flushAnalytics` у G09.02): экранная хваля (M5/G06) і
  pipeline-лічбы (AR-5 «адзін дастаўнік лікаў») кампануюць іх, калі з'явяцца;
  порт checker-а + дэфолтаў уводзіцца wiring-ам — кантрактны модуль node-side
  (яго reader чытае файлы), таму дакумент і checker інжэктуюцца
  (`services/config.ts` G07.05 прэцэдэнт; тыпавая паверхня —
  `remote-config.d.mts`).
- **Дэфолтныя лічбы:** `dwell_ms: 6000` і `accuracy_gate_m: 40` — лікі канона
  даслоўна (`10` разд. 6 «Ацэнкі, а не факты», табліца каліброўкі;
  `core/pipeline` `defaultPipelineConfig`); `trigger_radius_default: 40` —
  рэзерв для кропкі без аўтарскага радыуса (маштаб дэма-фікстуры, G07.04
  табліца лічбаў); `moment_cooldown_min: 10` — гіпотэза «1 Moment на ~10 хв»
  (`05` разд. 12); `moments_per_session_max: 2` і `min_app_version: 1` —
  прапановы без кананічнага ліка. Усе прапановы пазначаныя ў description
  схемы; палявая каліброўка — G11.02.
- **Серверны бок `GET /v1/config` — `not-run`:** крытэрыі issue — кліенцкія
  (праверка адказу, кэш, дэфолт); Deno-wiring па прэцэдэнце G08.01/G09.02 —
  падчас дэплою, калі праект Supabase будзе падключаны.
- **Crash-звіты не маюць сервернага эндпоінта ў `09` §5** — прызначэнне
  толькі праз інжэктаваны sink; чаргі/захавання звітаў тут не ўводзіцца.
- **Прадакшн-драйвер** (expo-sqlite) — `not-run` (TR-10, `23`); тэсты ідуць
  на node:sqlite праз той самы мінімальны паверхню драйвера (G04.01/G09.01).
