# G20.06 — вынік: сакрэт толькі па правераным HTTPS, 2026-10-02

Задача [#477](https://github.com/vokhandcrafts/KUDY/issues/477), спецыфікацыя [network-privacy.md §N3](../../specifications/architecture-hardening/network-privacy.md), эпік #470. Галінка `zcode/477` ад main `cdb7c2b` (перабазаваная пасля мержу #512).

## Што зменена

Дэфект (межы доказу з задачы, аўдыт A26-06): дэфолтныя прадукцыйныя транспарты `services/analytics.ts` (fetch у `defaultHttpTransport`) і `services/device.ts` (fetch у `defaultTransport`) адпраўлялі запыт на адвольны канфігурацыйны `baseUrl` без праверкі разабранага URL — `http://example.invalid/functions/v1` атрымліваў `Authorization: Bearer <device_secret>`, рэгістрацыя аддавала `device_secret` у адказ па тым жа канале, і fetch маўкліва ішоў за перанакіраваннем (другі аўтарызаваны запыт).

- **Адзіны ўладар праверкі** — новы `services/secure-url.ts`: `parseSecureEndpointUrl` (разабраны URL: parseable, толькі `https:`, без `username`/`password`) і `assertNotRedirected` (фінальны `response.url` ≠ запытанага → адмова). Паведамленні называюць парушэнне і мяжу, але не эхо-яць адхілены URL — ён можа несці credentials, якія не павінны трапіць у журнал (N3).
- **`services/device.ts`** — дэфолтны транспарт рэгістрацыі (адказ нясе `device_secret`): валідацыя да `fetch`, сам fetch з `redirect: 'error'`, адказ з чужым фінальным URL адхіляецца да чытання цела — сакрэт з перанакіраванага адказу не захоўваецца. Новае імя адмовы `DeviceError.rule = 'unsafe_endpoint'` (да сеткі і для рэдырэкт-адмовы); астатнія правілы і статусныя мапінгі без зменаў.
- **`services/analytics.ts`** — дэфолтны HTTP-транспарт адпраўкі падзей: тое самае, плюс `Authorization` дасягае `fetch` толькі пасля праверкі (загаловак збіраецца выклікаючым `createEventsTransport`, але жывы выклік — толькі праз правераны `postEvents`). Новае імя адмовы `AnalyticsError.rule = 'unsafe_endpoint'`.
- Ін'ектаваныя транспарты (тэставыя порты) не зменены; паводзіны на валідным канфігураваным HTTPS — тыя самыя (201/200, разбор цела, закрытыя статусныя мапінгі).

## Па крытэрах

1. **HTTP, malformed URL і URL-credentials адхіляюцца да fetch; нуль сеткавых выклікаў з сінтэтычнымі сакрэтамі.** `G20.06 N3: http, malformed and credential URLs are rejected before any network call` (device) і `G20.06 N3: secret-bearing events requests reject unsafe endpoints before any network call` (analytics): fetch-стаб лічыць роўна 0 выклікаў на тры класы адрасоў (`http://example.invalid/...`, `not a url at all`, `https://user:pass@example.invalid/...`), `secretStore` нічога не захоўвае, дыягностыка `unsafe_endpoint` не эхо-іць URL (асобныя адзінкавыя тэсты ўладара + праверка ў analytics-сьюце). Сакрэты ў фіксчурах — сінтэтычныя (`secret-value`, ідыёма wire-фіксчуры G09.02).
2. **Рэдырэкт не пачынае другі аўтарызаваны запыт; валідны HTTPS захоўвае паводзіны.** Двайная ахова: (а) кожны сакрэтны fetch ідзе з `redirect: 'error'` — стаб фіксуе `init.redirect` у трох тэстах, і калі платформа адмову паважае, адказ мапіцца ў `network_failed` (`G20.06 N3: when the platform refuses the redirect…` ×2); (б) калі платформа опцыю праігнаравала і вернула адказ з чужым фінальным URL — `assertNotRedirected` адхіляе адказ да чытання цела, другога выкліку з нашага кода няма, `secretStore` не захоўвае сакрэт з чужога адказу (`G20.06 N3: a response redirected away from the endpoint is not accepted` ×2). Валідны шлях праз рэальны дэфолтны транспарт: 201-рэгістрацыя з захаваннем identity (`…registers through the default transport with redirect refused`), 200-адпраўка з правераным Bearer-загаловкам (`…keeps the wire behavior with redirect refused`).
3. **Іншыя аўтарызаваныя транспарты прагледжаныя** — табліца вышэй; агульная мяжа ўжытая толькі там, дзе ёсць прадукцыйны сеткавы выклік з сакрэтам; дублявалідатараў няма.
4. **Тэсты ў стандарным камандзе і падаюць на реверце.** 14 новых тэстаў у трох файлах (glob `services/**/*.test.ts` ужо ў runner-е `npm test`); реверц-эксперымент ніжэй; у логах і дэмо-вывадзе рэальных сакрэтаў няма.

## Межы платформы (запісана як абмежаванне, не як поўная гарантыя)

`redirect: 'error'` — стандартная паводзіна WHATWG fetch. Платформа, што ігнаруе опцыю і ідзе за рэдырэктам на натыўным узроўні (часты выпадак RN-стэкаў), ловіцца `assertNotRedirected` — адказ адхіляецца і сакрэт з яго не захоўваецца, але сам пераход на платформавым узроўні да гэтага ўжо адбываецца; OkHttp пры гэтым здымае `Authorization` пры cross-host рэдырэкце. Другі аўтарызаваны запыт з кода KUDY немагчымы (тэст фіксуе роўна адзін выклік), ноў-сэкандары на ўзроўні натыўнага стэка — такія, як дазваляе платформа.
