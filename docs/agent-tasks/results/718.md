## Acceptance evidence

1. **Reproduction outside the recorded probe rows.** The minimal case (one raw uncapped `Text`, nothing else) reproduces the scaling anomaly deterministically at font_scale 2.0: glyph advance 74px = **1.762×** of the 42px base, while the linear expectation (and the pinned `allowFontScaling=false` row at double size, measured 84px) is **2.0×** (`analysis.json`: `non_linear_ratio` 1.762 vs `linear_ratio` 2.0). The font family is not a factor: the no-fontFamily row measures identically (74px). At font_scale 1.0 the same row renders correctly (42px = 1.0×, 16 glyphs, no clip). **The wrong-glyph artifact itself reproduces on the recorded G21.47 surface** (`probe-scale2.png`, the `scale-raw-full` row): the glyph at U+53F2 loses its bottom stroke at the view boundary and reads as an \u7535-like shape, \u9EC4 reads \u82D7-like, \u91D1 reads \u4F59-like — `glyph-53f2-clip-compare.png` shows the clipped and correct U+53F2 side by side. The minimal surface does NOT clip (its raw rows measure 214px — the full correct height) — the clip needs the context recorded below, which is why the G21.47 surface showed it and the isolated row alone does not.
2. **Root cause, RN/framework level, source-anchored.** Two independent defects stack in the uncapped path on Android 14+ (this AVD: API 36):
   - **The size anomaly (advance ≈1.8×).** RN 0.81.5 converts the uncapped font size through the framework SP pipeline: `TextAttributeProps.java:439-442` (fontSize → px via `PixelUtil.toPixelFromSP`) → `PixelUtil.kt:41` (`TypedValue.applyDimension(COMPLEX_UNIT_SP, ...)`) → AOSP `TypedValue.java:432-437`: on API ≥34 with non-linear font scaling active, SP conversion goes through `metrics.fontScaleConverter.convertSpToDp(value)` — the accessibility curve maps the user's font_scale 2.0 to ≈1.76× for 16sp text instead of 2.0×. The pinned path converts via DIP (`TextAttributes.kt:72`, `PixelUtil.kt:17-24`) and stays exactly 2.0× (84px measured); the capped path clamps with `min(scaledValue, value×density×multiplier)` (`PixelUtil.kt:43-44`) and lands on 1.25× as designed. The accessibility string stays correct at every scale (uiautomator text = the 16-char string; `raw-*.json` `textLength`).
   - **The wrong-glyph clip (view-height poisoning).** On the recorded probe surface the uncapped row's view measures 996×**78**px — one line at ≈52.5px em with CJK fallback line metrics — which is the **capped** row's size (`min(74, 16×2.625×1.25) = 52.5px`), not its own (its correct measure is 2 wrapped lines at 74px em ≈ 214-220px, as the minimal surface's identical row proves). The only code path where a foreign paint enters a view's measure is the Fabric attributed-string cache branch: `TextLayoutManager.kt:645-653` (`AS_KEY_CACHE_ID` → paint from `ReactTextPaintHolderSpan.textPaint`, the Spannable served by `tagToSpannableCache`, lines 103-111/472-473). The draw uses the row's own attributes (`createPreparedLayout` → `newPaintWithAttributes` = 74px em, 2 lines, `setUseLineSpacingFromFallbacks(true)`, lines 577-579) → ~220px of content painted into the 78px view → the ink is hard-clipped at the view bottom (device-measured: ink profile ends at y=2095 with 253px of ink in the last row, view bottom y=2096, no taper — `analysis.json` `probe_raw_clip`), cutting the bottom strokes that distinguish \u53F2/\u9EC4/\u91D1. Scale 1.0 cannot show the defect: all three paths converge at 42px, so a shared paint measures identically. The upstream `TextLayoutManager.kt:410-411` TODO ("Should this be using effectiveFontSize instead of fontSize?") already flags the divergence family; the exact Fabric-side cache-id assignment policy (why the probe surface's rows shared and the minimal surface's did not) is C++-internal and is the one detail this task leaves to upstream.
3. **The bound: production stays safe; zh stays gated.** The app idiom (G06.05) routes user-facing text through `ScaledText` (cap = `font.big-text-factor` 1.25) — device-verified immune at font_scale 2.0 (`probe-scale2.png`: the capped and pinned rows render correctly on the same screen where the uncapped row clips). The affected uncapped path exists only in the dev-only probe surfaces; production zh remains behind the G21.50 release flag, which is the natural gate until upstream changes. Decision recorded: **no production code change; the bound is the existing ScaledText idiom + the G21.50 flag**, and the defect class (uncapped `Text` + font_scale ≥2.0 + CJK fallback on API ≥34) must not be reintroduced into production surfaces — `components/scaled-text.tsx` is the single rendering idiom to keep. Filing the measure/cache divergence upstream to facebook/react-native is an owner decision (the two source cites above are the report's core); ⏭️ out of scope here.
4. **Resolution pointer in the G21.47 results file.** Appended to `docs/agent-tasks/results/G21.47.md` (dated, linking this file and the PR) per implementation-rules 8 — history untouched.
