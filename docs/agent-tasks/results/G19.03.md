# G19.03 — трывалае сховішча карпуса і аднаўляльныя рэзервовыя копіі (issue #460)

2026-10-02, ZCode (GLM-5.3-Flash), галінка `zcode/460` ад main @ db9b3f8.

## Што зменена

- `tools/corpus/store.mjs` — новы: лакальная SQLite-база карпуса на `node:sqlite` (ідыём `tools/collector/store.mjs`: `PRAGMA foreign_keys = ON`, FTS5). Плюс да калектарскага ідыёму — тое, што патрабуе 25 §9: версіянаваныя міграцыі (`corpus_schema_migrations`, спіс `CORPUS_MIGRATIONS`) — write-блак бярэцца ПЕРад здымкам (busy адказвае `db-busy` да ўсякага пісання і нічога не адкочвае ў чужой сесіі), здымак — `VACUUM INTO` з другой сесіі пад нашым блакаваннем; няўдалая міграцыя — транзакцыйны rollback (DDL у SQLite транзакцыйны, байты файла не мяняюцца), здымак застаецца на дыску як аднаўляльная копія; `PRAGMA busy_timeout = 0` + пераклад SQLite-памылак у названыя дыягностыкі (`db-busy`, `foreign-key-violation`); усе запісы праз `BEGIN IMMEDIATE`-транзакцыі, якія коміцяцца да вяртання (ніякая транзакцыя не трымаецца адкрытай падчас чакання мадэлі — у сховішча наогул няма сеткавай паверхні). API: `openCorpus`, `closeCorpus`, `registerPackage` (паўторная рэгістрацыя тых жа ідэнтыфікатараў з іншым дакументам → `package-document-mismatch`, не ціхі no-op), `storeModelResult` (узровень 1; паўторны store таго ж run замяняе машынны вынік цалкам, entities/mentions — cascade), `deleteModelResults` (мінімум адзін scope, інакш `delete-scope-missing`; кідае толькі машынныя радкі), `recordIdentityDecision`/`latestIdentityDecisions` (аўтарскія рашэнні — асобная табліца без сувязі з машыннымі радкамі), `saveCase`/`getCase`, `rebuildSearchIndex` (вытворны FTS5-індэкс, перабудова з захаваных фрагментаў), `listLibraryPackages` (зваротнае чытанне дрэва бібліятэкі ў той жа packageRecord, што вяртае `importArticle`; extractor version — два ўзроўні каталогаў `profile/vN`).
- `tools/corpus/backup.mjs` — новы: `backupCorpus(store, {libraryRoot, outDir})` — узгоднены здымак базы праз `VACUUM INTO` + патрэбныя файлы пакетаў (пералік з БД: raw.html, article.json, text.md, выявы) + `manifest.json` з SHA-256. Рэгістрацыйныя анкеры правяраюцца падчас копіравання: raw.html мае хэшаваць у revision_id, выява — у asset_id, article.json — супадаць з зарэгістраваным дакументам. `restoreCorpus({backupDir, newLibraryRoot})` — поўная верыфікацыя маніфеста ДА стварэння мэты, мэта толькі свяжая (існуючая адхіляецца), пасля копіравання — `PRAGMA integrity_check` + `PRAGMA foreign_key_check`; пры любым збоі створанае выдаляецца. Шляхі з маніфеста правяраюцца строгім узорам (толькі content-derived компоненты) — падроблены маніфест не можа назваць шлях па-за дрэвам; негатыўны тэст `tampered_manifest` (traversal-шлях → `unsafe-backup-path`, крывы JSON → `backup-manifest-missing`; мэта ніколі не ствараецца).
- `tools/corpus/cli.mjs` — дададзеныя радкі плана G19.03: `import --db --library-root` (рэгістрацыя ўсіх поўных пакетаў з дрэва; ідэмпатэнтная, як unpack), `backup --db --library-root --out`, `restore --backup --library-root`. Коды выхадаў і гігіена журналу — тыя самыя, што ў астатніх каманд (толькі правілы/класы памылак, без прыватных шляхоў).
- `tools/corpus/fixtures/packages.mjs` — новы агульны сінтэтычны фікстурны модуль (дыскавая бібліятэка з байт-анкерамі + узровень 1 з фікстуры); выкарыстоўваюць backup- і cli-тэсты.
- `tools/corpus/{store,backup}.test.mjs` — новыя паводзінавыя сюіты з імёнамі з брыфа; `tools/corpus/cli.test.mjs` — дададзены end-to-end тэст новых каманд праз рэальны spawn.
- Журналістыка npm test не мяняецца: glob `"tools/corpus/*.test.mjs"` ужо існаваў (G19.01).

## Крытэрыі

### 1. Паўторная рэгістрацыя не стварае дубляў; вонкавыя ключы адхіляюць сіроць

- `store.test.mjs` → `duplicate_registration`: другі `registerPackage` вяртае `alreadyRegistered`, лічбы ўсіх табліц (articles/revisions/extractions/fragments/media_assets/extraction_media/extraction_links) застаюцца роўнымі першасным.
- `orphan_fragment`: фрагмент з чужым revision_id → `orphan-fragment` да першага радка (нулявы стан БД пасля адмовы); выява з невядомым asset_id → `orphan-media`. `PRAGMA foreign_keys = ON` пініцца тэстам migration-кантракту; каскад і сіроты ловяцца перакладам SQLite-памылак у `foreign-key-violation`.

### 2. Entities і mentions асобныя; неапрацаваныя згадкі і падзел асоба/сям'я захоўваюцца; пацверджаныя рашэнні перажываюць замену машыннага выніку

- `unresolved_mention`: згадка без `proposed_entity_id` захоўваецца з NULL (unresolved); з прапановай — змоўлена да entities свайго выніку. Person і family — дзве розныя радкі з розным kind (25 §5: чалавек і сям'я не зліваюцца).
- `decisions_survive_reindex`: рашэнне аўтара трымаецца ў `identity_decisions` (без FK на машынныя радкі); `deleteModelResults` і поўная замена машыннага выніку таго ж run не чапаюць яго; `latestIdentityDecisions` чытае пацверджаны стан пасля абедзвюх аперацый.

### 3. Перабудова індэкса і зняцце машынных вынікаў захоўваюць Cases і рашэнні; транзакцыі коміцяцца да знешніх запытаў

- `rebuildSearchIndex` перапісвае толькі `corpus_fts` (вытворны стан); у `decisions_survive_reindex` пасля перабудовы і зняцця Case і рашэнне застаюцца.
- Сховішча не мае сеткавых выклікаў; кожная мутацыя — адна `BEGIN IMMEDIATE`…`COMMIT` транзакцыя, якая завяршаецца да вяртання з функцыі (25 §9). Гэта пінюць усе тэсты API: ніводны выклік не вяртае да адкрытай транзакцыі.

### 4. Другая пісьмовая сесія атрымлівае дыягностыку занятасці; няўдалая міграцыя пакідае аднаўляльную копію

- `writer_lock`: `BEGIN IMMEDIATE` першай сесіі трымае блак; другая сесія атрымлівае `db-busy` (не падвісанне і не ціхую чаргу); пасля зняцця блока той самы запіс праходзіць.
- `failed_migration_keeps_backup` (backup.test.mjs): зламаная міграцыя v2 → `migration-failed`, файл `<db>.pre-migration-v2` захаваны, паўторнае адкрыццё чытае v1 са ўсімі данымі (extractions, identity_decisions), спіс прымененых версій — `[1]`.

### 5. Рэзервовы пакет — узгоднены здымак + файлы + маніфест сум; аднаўленне толькі ў свяжы каталог; пашкоджаная копія не перацірае жывую бібліятэку

- `restore_roundtrip`: backup (≥5 файлаў + manifest.json) → restore ў свяжы каталог → пераадкрыццё БД: машынны вынік, згадка, дзве асацыяцыі выяваў, рашэнне аўтара, Case — усё на месцы; паўторная рэгістрацыя пакета ў адноўленай бібліятэцы — `alreadyRegistered`; паўторны restore ў тую ж мэту → `restore-target-exists`.
- `corrupt_checksum`: адзін перавернуты байт у скапіяваным файле → `backup-checksum-mismatch`, мэта НЕ створаная; адсутны файл з маніфеста → `backup-file-missing`, мэта таксама не створаная. Анкеры цэласнасці: raw.html→revision_id, выява→asset_id, article.json→зарэгістраваны дакумент (адхіленне → `backup-file-mismatch`/`backup-document-mismatch`).
- Рэферыі з маніфеста правяраюцца строгім узорам шляхоў (`unsafe-backup-path`) — падроблены маніфест не выходзіць за дрэва бэкапу.

## Out of scope kept

- Калектарская БД не мігрыраваная; множмашынны sharing і воблака — па-за межамі; зліццё па прозвішчы — па-за межамі (25 §5).
- Search/selection над індэксам, мадэльныя запыты, export — гэта G19.04–G19.07; сховішча дае толькі табліцы/API.
- `tools/corpus/README.md` — G19.09 (план: фінальны usage).
- Рэальныя крыніцы і прыватныя шляхі ў Git не трапляюць: усе тэсты — на сінтэтычных фікстурах, часовыя каталогі чысцяцца ў `t.after`.

## Platform limitations

- `node:sqlite` — engines `>=22.19.0`: модуль без сцяга з 22.13, CI-матрыца 22/24 пакрытая; FTS5 у bundled SQLite ужо выкарыстоўваецца калекторам (гэта праверана CI). Windows-прагон не рабіўся; шляхавых параўнанняў, залежных ад separator, у сховішчы няма (node:path + realpath containment, як у G19.02).
