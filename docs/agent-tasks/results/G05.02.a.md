# G05.02.a — Location pipeline and geo helpers (pure)

Issue #210 · branch `zcode/210` · 2026-09-24 · executor: Zcode session (GLM-5.3-Flash).

The first production slice of the location side lives in `core/pipeline/` and
`core/geo/`: `types.ts` (FixInput, PipelineCandidate, PipelineConfig,
PipelineState, the event/reason unions), `pipeline.ts` (the five 09 §6.2
stages as one pure `acceptFix()`), `haversine.ts` (distance in meters) and the
acceptance suites `pipeline.test.ts` / `haversine.test.ts`. The pipeline emits
the engine's `LocationAccepted` / `DwellCompleted` forms (19 §3.3, the
G05.01.a event union) and owns only the smoothing window and the dwell
accumulators (19 §2.1); it knows nothing about `heard` / `auto_fired` (AR-5,
19 §1.3) and does not duplicate the engine's trigger-border re-checks
(freshness ≤ 30 s, `accuracy ≤ radius`, deferred ≤ 2 × radius — ADR G01.01
§4.8, `core/engine/reducer.ts` fixWithinDistance). The engine, run-model and
spike files were not edited; the spike's 15 s freshness stays a spike value
(19 §1.3 table).

## Canon deviations resolved in-code (implementation-rules 2/6)

Anchored in the `types.ts` header, restated here for the reviewer:

1. **Candidates carry coordinates + radius.** 19 §3.3 sketches
   `candidates: ReadonlyMap<StopId, number>`; a bare number cannot evaluate
   candidates on the smoothed point (09 §6.2 stage 4: «кандыдаты па
   згладжанай кропке») nor order simultaneous completions by distance (AC 5).
   The map value is `PipelineCandidate { lat, lng, radius }`.
2. **State is threaded explicitly; `now` is a parameter.** The owned state
   (19 §2.1 row) travels as `previous → result.state`, the engine `step()`
   precedent (19 §3.1), which is what makes AC 1's deep-equal claim directly
   testable; `now` rides along because the future-timestamp check (AC 6,
   19 §3.3 FixInput «будучыя … значэнні не прымаюцца») has no other source —
   the pipeline reads no clock (AC 7).
3. **Rejection answers a discriminated result, never throws** (AC 6):
   `{ accepted: false, reason }` with one named reason per failed check, or
   `{ accepted: true, fix, events }` — the canon result shape (`fix`, first
   event `LocationAccepted` carrying the accepted fix) preserved on the
   acceptance branch.

## Acceptance criteria — walked from the card

1. ✅ **Stage order is fixed and each stage rejects before any state
   mutation.** Order: corrupt-input validation → accuracy gate → spike
   rejection → smoothing → dwell/candidates (09 §6.2 stages, validation
   first — a NaN accuracy must not reach the gate). Every rejection returns
   the previous state object unchanged; acceptance builds a fresh window
   array and dwell map (copy-per-accumulator), so the input is never
   mutated. One deep-equal test per rejecting stage (`pipeline.test.ts`,
   «criterion 1: …»), plus two order-pinning tests: corrupt beats the
   accuracy gate, the accuracy gate beats spike rejection. Deep-equal tests
   keep passing after the machine state grew (window + non-empty
   accumulator fixture).
2. ✅ **Accuracy gate and spike rejection with bounds on both sides.**
   40 m accepted / 40.01 rejected («criterion 2: accuracy …»); implied speed
   at ±1 % around 12 km/h on increasing time (the exact arc comes from the
   same haversine, the time margin keeps the case off float dust);
   displacement 4.99 m accepted / 5.01 m rejected on non-increasing time
   (Android batching). The canon numbers (40 m, 12 km/h, 5 m, window 3) are
   canon constants in `pipeline.ts` and pinned as literals in the tests.
3. ✅ **Smoothing is the plain mean of the last 3 accepted coordinates.**
   Hand case walks 4 fixes and asserts each smoothed point equals the window
   mean and the oldest fix drops after three («criterion 3: smoothing …»);
   the seeded property test (mulberry32, 300 steps) asserts the smoothed
   point equals the window mean and never leaves the window's bounding box.
4. ✅ **Dwell on the smoothed point, reset on leaving, once per continuous
   dwell, `dwell_ms` from `PipelineConfig`.** The completion test walks a
   standing person: exactly one `DwellCompleted(stopId, radius)` at the fix
   where the accumulator reaches `dwell_ms`, none afterwards while staying
   («criterion 4: dwell completes once …»). The reset test walks out and
   back at a pace that respects both the 12 km/h gate and the smoothing lag:
   a kept accumulator would fire on the reset fix itself, the restarted one
   fires nine steps after re-entry. The smoothed-point test places the raw
   fix outside a 10 m radius while the smoothed point stays inside — the
   accumulator grows on the smoothed judgment («criterion 4: dwell judges
   the smoothed point …»). `defaultPipelineConfig.dwellMs === 6000` pinned;
   a per-call config completes earlier.
5. ✅ **All passed-in stops get distances; simultaneous completions ordered
   by distance, then stop_id.** Distances are computed for every candidate
   regardless of radius hit («criterion 5: distances cover every passed-in
   stop …»); the ordering test builds a 20 m three-way tie (two identical
   offsets plus a symmetric southern point) under a 0 m and a 40 m stop, so
   alphabetical order would fail it. The seeded property test re-runs the
   same walk over 10 shuffled candidate maps and asserts identical results.
6. ✅ **Corrupt input rejected with named reasons, never thrown.** Isolated
   one-violation tests per reason (implementation-rules 14):
   `non-finite-coordinate` (NaN/±Infinity lat and lng), `latitude-out-of-range`
   (±90.01 rejected, ±90 accepted), `missing-accuracy` (absent/NaN/Infinity),
   `negative-accuracy`, `non-finite-timestamp` (absent/NaN/Infinity),
   `future-timestamp` (`at > now` rejected, `at === now` accepted).
7. ✅ **`core/` imports nothing from React Native, the network, the disk or
   the clock.** The only imports are relative `core/` files and, in tests,
   `node:test`/`node:assert` (the core-test exemption). Machine-checked:
   `npm run arch:check` green (below).

## Proof

«Move the accuracy gate after smoothing → the "rejected fix leaves the
window unchanged" test fails» — executed in the shipping session: with the
gate moved after the window is built (rejection returning the built window),
`pipeline.test.ts` fails
«criterion 1: an accuracy-gate rejection leaves the window and dwell
accumulators deep-equal» — together with the two tests that pin the gate's
position (stage order and the 40 m bounds) — and passes again after the
revert. The haversine suite fails when the `cos(lat)` factor
is dropped — verified by the same kind of revert run: only the cos-factor
test catches it (the equator-arc case cannot, `cos(0°) = 1`), which is why
that test asserts a bounded ratio at latitude 54 instead of a single arc.
