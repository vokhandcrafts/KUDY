# G21.03 result — Show a localized message when the web map fails

Date: 2026-10-03 (claim 2026-10-03T18:21:06Z). Branch: `zcode/536` from main `25e55e0`.

## What was changed

The map component already marked init failures on the container
(`data-map-error`) but stayed a silent empty box for the visitor. The failure
path now renders a localized accessible message beside the empty map, and a
successful initialization clears both the marker and the message:

- `web/components/city-map.tsx` — `CityMap` renders `<p role="status" hidden>`
  fed by the new required `errorText` prop; `fail()` unhides it together with
  the existing `data-map-error` marker, `succeed()` removes both. The state
  rule: only pre-load errors flip the map into the failure state — once
  `load` fired, the map is initialized and working, so later transient tile
  errors stay console-only. Unmount cleanup (disposed flag + `map.remove()`)
  unchanged.
- `web/lib/i18n/index.ts` + `be.ts` / `en.ts` / `uk.ts` — one new key
  `mapError` in the typed `UiStrings` catalog; all three string files get it
  (the type system and the key-set parity test are the enforcement, see
  Decisions).
- `web/components/map-page.tsx` — passes `strings.mapError` as `errorText`.
- `web/city-map.browser.test.ts` + `web/test-browser/` (`cdp-browser.mjs`,
  `map-harness-server.mjs`, `map-harness.tsx`) — the browser proof, no new
  dependencies: it drives a locally installed Chromium (KUDY_CHROMIUM
  override, then common binary paths) over raw CDP using the WebSocket client
  built into Node, serves the real `MapPage` component graph compiled in
  memory with the workspace's own `typescript` package, loads React's CJS
  production builds and MapLibre's UMD build straight from `web/node_modules`
  through tiny import-map shims, and fulfils the provider style request from
  a deterministic local style — no real network, no provider account, no
  tile traffic.

## Acceptance criteria walk

1. **Abort map requests with internetdisconnected and reproduce the empty map with only data-map-error.** CDP `Fetch.failRequest` with `errorReason: "InternetDisconnected"` (the protocol spelling of the issue's "internetdisconnected") aborts the `tiles.openfreemap.org/styles/liberty` request. The map area renders no tile content; the container carries `data-map-error` and nothing else marks the failure — the DOM of the failure state contains no raw failure text (asserted against `openfreemap|http|failed to fetch|typeerror`).
2. **Render a localized accessible failure message; clear it after successful initialization and clean up map resources on unmount.** The message is a `<p role="status">` (polite live region) unhidden on failure with exactly `be.mapError` on the be mount and `en.mapError` on the en mount — the strings come from the real locale files, not from the test. A successful load sets `data-map-ready="fitted"`, deletes `data-map-error` and hides the message again. Unmounting the live map leaves zero `window` error/unhandledrejection records and zero new console errors within the observation window.
3. **Test provider rejection, successful load and recovery; no raw exception/URL is shown to visitors and guide links remain usable.** All three scenarios run against one page in one browser session: aborted provider (both locales), fulfilled local style (success), and remount success after a failed mount (recovery — MapLibre does not retry a failed style fetch inside one instance, so a fresh initialization is the recovery path). In every scenario the two guide links rendered by the real `MapPage` from the fixture data are visible and pass the `elementFromPoint` hit test — nothing overlays them, and the failure text shows only the localized message.
4. **The visible-error assertion fails when the fix is reverted.** Revert experiment ran in this session: `web/components/city-map.tsx` temporarily restored to the pre-fix version (no message rendering); the suite fails on the visible-error assertion (`messageText` strict-equal to `be.mapError`) while the legacy `data-map-error` marker still sets; restoring the fix returns the suite to green. The fail-on-revert proof also lives in the Showboat demo below.

## Decisions recorded

- **`uk.ts` receives the key although the issue names be/en only.** The typed `UiStrings` catalog and the key-set parity test (`pages.test.ts`) are the contract owner: a key added to be/en only cannot typecheck. The Ukrainian sentence rides the same mechanical parity as every other key.
- **Recovery means the next initialization, not a retry timer.** MapLibre does not re-fetch a failed style inside one map instance; inventing a retry loop would add behavior no criterion asks for. The test proves the failed state is left cleanly and the next mount succeeds with no stale message.
- **Post-load tile errors stay console-only.** AC 2 says "clear it after successful initialization"; a single lost tile after a working load must not flip the map back into the failure state — the message would otherwise lie about a map the visitor can still use.
- **The test sits at `web/` root, not `web/components/`.** The URL guard in `web/lib/content/pages.test.ts` scans every file under `web/app` and `web/components` for literal `https?://`; the harness intentionally contains the provider URL pattern, so the file lives beside `web/privacy-page.test.ts` — outside the guarded trees.
- **No browser-automation dependency added.** The repo's test stack has no Puppeteer/Playwright; the proof uses the DevTools protocol over Node's built-in WebSocket and skips visibly (implementation-rules 7) when the host has no Chromium binary or no `web/node_modules` — on such hosts the named planned test reports a skip reason, never a silent pass.
