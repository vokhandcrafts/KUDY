# G17.16 result — гард сеткавага шляху: толькі публічныя http/https адрасы

- Status: `complete`
- Task: issue #375, branch `zcode/375` (worktree `KUDY-wt-375` off `main` @ b01cced)
- What: new `tools/collector/netguard.mjs` — `createNetGuard({ resolve })`
  stands before every real collector network request: the crawl step fetch
  (crawler.mjs, after the fence/depth re-check and before the robots gate —
  the robots.txt fetch is itself a network request, G17.15), both wiki step
  handlers (runloop.mjs, before `loadApi`), and the video cover fetch
  (youtube.mjs, inside `createYoutubeFetch`). The guard refuses a URL whose
  scheme is not http/https or whose host — an IP literal classified directly,
  otherwise resolved over DNS with every returned address checked — lands in
  loopback, RFC1918, link-local, ULA, unspecified, multicast, CGNAT,
  benchmarking or documentation space; an unresolvable host and an
  unparseable address refuse too (fail closed). Refusals are named
  diagnostics («net guard: <host> … — request not made»), the step goes to
  `failed` in run_log, and the run continues. The `resolve` boundary is the
  test seam — no test touches the network; suites that fetch loopback
  fixtures stand the guard down explicitly.

## Proven (criteria of issue #375)

1. **Private/reserved addresses refused before any request** —
   `netguard.test.mjs` pins every range the issue names (127.0.0.1, ::1,
   10/8, 172.16–31/12, 192.168/16, 169.254/16, 0.0.0.0, fd00::/8) plus
   neighbouring blocks (multicast, ULA fc00::/7, CGNAT 100.64/10,
   benchmarking 198.18/15, documentation, IPv4-mapped literals judged by
   their embedded address) with public boundary addresses passing
   (172.15/172.32, 100.63/100.128). Pipeline-level: a campaign with loopback
   and RFC1918 seeds runs the production handlers with a fetcher spy that
   fails on any call — it is never called; the guard runs inside `crawlStep`
   after the fence re-check, so a refusal means no fetch, no politeness wait,
   no bytes.
2. **Unknown host is a readable diagnostic, not a crash** — a seed whose
   resolver answers ENOTFOUND fails as
   `crawl <url>: net guard: missing.example did not resolve (ENOTFOUND) —
   request not made`; the neighbouring public seed in the same campaign
   collects exactly as before, the run completes.
3. **Public addresses work as before** — the same campaign proves the public
   seed's fetch and snapshot are untouched; `file://` fixtures never reach
   the guard (a guard stub that throws on any call runs a full `file://`
   campaign green), and every pre-existing suite that fetches loopback
   fixtures stays green with the guard stood down.
4. **Refusals are recorded in the step journal, like other diagnostics** —
   run_log rows carry the full reason (`net guard: 127.0.0.1 is a loopback
   address — request not made`) with the existing step-context prefixes
   (`crawl <url>: …`, `wiki-article '<title>': <requestUrl>: …`,
   `thumbnail <url>: …`). A refusal writes no fence-audit line — the audit
   records fence decisions only; a test pins the audit file's absence.
   Like every failing crawl step, a refusal counts toward the error series:
   the CLI suite's error-series run is now driven by four loopback seeds —
   three refusals stop the run with the diagnostic on stderr, exit code 0,
   the fourth seed stays `pending`.
5. **Campaign-driven tests, red on revert** — `netguard.test.mjs` drives
   campaigns through `runCampaign` with the production handlers (resolver
   injected), plus wiki (api on 127.0.0.1 refused by the real production
   handlers — an IP literal needs no DNS) and youtube (cover URL on
   127.0.0.1 refused before `loadThumbnail`). Revert experiment: with the
   guard's verdict neutered, 8 of 12 guard suites fail (the range table
   unit tests still pass — classification is pure); restored, 12/12 pass.
