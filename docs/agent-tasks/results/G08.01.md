# G08.01 — Device-рэгістрацыя і серверная ізаляцыя

Задача: issue [#64](https://github.com/vokhandcrafts/KUDY/issues/64) (backlog-радок G08.01 з `16_delivery_backlog.md` §G08, атамарнага файла не існавала). Выканаецца: ZCode (GLM-5.3-Flash), 2026-09-22/23, клейм па Zcode-выключэнні issue-workflow §1 (`agent:running` + claim-каментар).

## Што зроблена

### Крытэрый 1 — сакрэт адзін раз, бяспечнае лакальнае сховішча, серверны хэш, rate-limit

- Сервернае ядро `supabase/functions/_shared/device-core.ts`: `registerDevice()` генеруе `device_id` (UUID) і `device_secret` (32 байты, base64url — форма спайку G00.03, ADR §2.1), захоўваецца толькі SHA-256 хэш; сакрэт вяртаецца кліенту раўн раз.
- Bearer-верыфікацыя `verifyBearer()` — адзіны auth-шлях для device-scoped эндпоінтаў; indexed lookup па хэшы (SQL) + `createMemoryLookup` з ідыёмай `timingSafeEqual` спайку для тэстаў/дэм.
- Rate-limit: фіксаванае акно 1 гадзіна па `sha256(IP)` (сыры IP не захоўваецца — `09` §6.1), лічыльнік у табліцы `device_registration_rate` (працуе праз інстансы Edge Functions). **Ліміт 20/г — рашэнне рэалізацыі**: кананічнага ліку ў `09` §5 няма («rate-limit па IP» без ліку); рэгістрацыя — адзін раз на ўстаноўку, таму 20/г шчодра для людзей і цягне ботафармы. Параметр у адным месцы (`DEVICE_RATE_LIMIT`), `429` з `Retry-After` да канца акна.
- Кліент `services/device.ts`: `ensureDeviceIdentity()` — рэгістрацыя адзін раз; сакрэт → injected `SecureSecretStore` (прадакшн-адаптар `services/device-secure-store.ts` на expo-secure-store ~15.0.8 з `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, `device_id` → зона B `device` праз новыя `setDeviceId`/`getDeviceId` у services/db (G04.01 схаванне). Першае захаванне — сакрэт, потым радок: збой паміж запісамі аднаўляецца свежай рэгістрацыяй (прыняты трэйд-оф да `/v1/link`, `09` §2).
- Deno-абгортка `supabase/functions/device/index.ts` (`POST /v1/device` ↔ `functions/v1/device`): fail-closed env-гейт `DATABASE_URL` (ідыёма спайку G00.03 §2.1), драйвер `npm:postgres@3.4.9` (пін — першы бэкенд-пін паводле прадказання G00.04.c), `429 rate_limited` / `404 not_found` / `500 server_error`.

### Крытэрый 2 — RLS закрывае прамы доступ кліента

- Міграцыя `supabase/migrations/20260922120000_device_tables_rls.sql` (табліцы з 19 §2.4, уласнік G08.01): `devices`, `entitlement_cache` (positive-only кэш, TTL `expires_at`), `event_log` (`event_id` — ключ ідэмпатэнтнасці, каскад на выдаленне прылады), `device_registration_rate`.
- Deny-by-default у два пласты: `REVOKE ALL … FROM anon, authenticated` + `ENABLE ROW LEVEL SECURITY` без пазітыўных палітык; `service_role` мае яўныя grants. Кліент (anon-ключ) не бачыць і не піша табліцы нават пры паўторным `GRANT` — гэта даказана паводзінна на сапраўдным Postgres (PGlite, in-process WASM, без Docker) у `supabase/functions/_shared/rls.test.ts`: anon-SELECT нябачны пры наяўным гранце, anon-INSERT → памылка RLS, service-role піша, каскад працуе.

### Крытэрый 3 — сакрэты і production-права не ў fixtures

- Усе сакрэты ў тэстах — runtime-генерацыя (`registerDevice()`, `random_bytes` у SQL-тэстах); ніякіх літаралаў.
- Гард `supabase/functions/_shared/fixtures-hygiene.test.ts` скануе `fixtures/`, `supabase/`, `web/public` (праз `git ls-files`): забарона JWT-літэралаў (`eyJ…`), прысваенняў значэнняў сакрэтным env-назвам (`REVENUECAT_SECRET_API_KEY`, `SERVICE_ROLE_KEY`, `DATABASE_URL`, …), 43-знакавых base64url-літэралаў (дакладная форма 32-байтнага сакрэту). Allowlist: `fixtures/discovery-contract/` (схемныя boundary-фікстуры G01.06 з наўмысна доўгімі радкамі — гістарычныя, гард G01.06 іх трымае).

### Крытэрый 4 — той самы auth для feedback, без дадатковай identity

- Адзіны модуль `device-core.ts` (`verifyBearer` + SQL-канстанты lookup-а) — тое, што `21` §2 называет «Auth» для `supabase/functions/feedback/` (G16.01): feedback-функцыя імпартуе той самы шлях, другой identity-сістэмы не ўводзіцца (нумар радка кантракта: `09` §5 — усе device-scoped эндпоінты, у тым лічбе feedback, маюць `Bearer <device_secret>`; `21` §2 — «прывязаныя да існуючай устаноўкі, без новага User-акаўнта»).
- Тэсты round-trip: `registerDevice()` → `verifyBearer("Bearer <secret>")` → `deviceId`; негатывы па ўсіх крывых формах загалоўка (ідыёма негатываў спайку G00.03.b).

## Не праверана (межы доказу)

- **Deno-абгортка** `supabase/functions/device/index.ts` — `not-run`: няма Deno/Supabase-праекта ў рэпазітары; runtim-праверка магчымая толькі пры першым дэплой (G11). Кантрактная логіка — у platform-neutral ядрі, даказаным тэстамі; SQL-выразы тыя самыя, што прагнаны на PGlite.
- **expo-secure-store на прыладзе** — `not-run` (G00.04-стыль): няма прылады/білда. `WHEN_UNLOCKED_THIS_DEVICE_ONLY` — OS-сцвярджэнне з дакументацыі, не прыладавы доказ. Тэсты сэрвісу ідуць праз injected адаптар (правіла 15: тэсты дасягаюць production-шляху services/device.ts; адаптар — тонкая OS-мяжа).
- **Rate-limit 20/г і Retry-After праз Supabase** — выбар рэалізацыі; на жывым праекце можа запатрабаваць перагляду па фактычным трафіку.
- **Live-клеткі G00.03** (пакупкі/restore) — па-за гэтай задачай (G08.03+).

## Рашэнні, за якімі варта сачыць наступніку

1. Бэкенд-піны: `npm:postgres@3.4.9` у функцыі; `@electric-sql/pglite@0.5.8` (devDep, толькі тэсты); `expo-secure-store@~15.0.8` (па `bundledNativeModules.json` expo 54). Наступны бэкенд-модуль (G08.02 grant) ўяўляе той самы `_shared` пакет і пін.
2. `supabase/` не скануецца arch:check (Deno; спіс каталогаў у script-е) — машынная праверка слаёў сервернага кода пакрыта тым, што ядро без Deno-API, а SQL — тэстамі; пры жаданні G08.02 можа дадаць supabase у арх-скан праз асобны config.
3. Міжсесійны інцыдэнт: падчас задачы паралельная сесія пераключала агульны checkout (zcode/155, zcode/179); мой каміт на гадзіну трапіў у чужую галінку і быў імі прыбраны; усе каміты сесіі — на чыстай базе ад origin/main (гл. PR- апісанне).

## Самарэвю (не незалежнае)

Scope: `git diff --numstat origin/main...HEAD` — 13 runtime/тэст файлаў + 3 дакументы + дэма; чужыя незакомічаныя змены (.gitignore, tools/collector/) у каміт не ўвайшлі. Primary concern — кантрактная дакладнасць: shape сакрэту/хэшу даслоўна з ADR G00.03 §2.1; статус-коды 429/404/500 — закрыты спіс; ліміт 20/г — пазначаны як выбар рэалізацыі з месцам змены; crash-window recovery — як прыняты трэйд-оф са спасылкай на `09` §2. Сакрэтаў у дыфе няма (fixtures-hygiene + gitleaks). Тэсты дасягаюць production-шляху: services/device.test.ts → services/device.ts → services/db (рэальная схема node:sqlite); RLS — праз рэальныя SQL-станы міграцыі.
