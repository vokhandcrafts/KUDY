# G20.01 — вынік: асінхронны SQL-лічыльнік у device/events, 2026-10-02

Выпраўлены дэфект аўдыту [A26-01](../../audits/2026-10-02-architecture-review.md)
([key: async-sql-result-not-awaited]): рэгістрацыя прылады чытала адказ
`db.unsafe()` як гатовыя радкі, прыём падзей перадавала `Promise<number>`
у сінхроннае параўнанне з лімітам. Галінка `zcode/472`, каміты `a8c0ff0`,
`5ab0f4a` на базе main `1ea14e2`. Задача: [#472](https://github.com/vokhandcrafts/KUDY/issues/472),
эпік: [#470](https://github.com/vokhandcrafts/KUDY/issues/470), спецыфікацыя:
[network-privacy.md](../../specifications/architecture-hardening/network-privacy.md), разд. N1.

## Што зменена

- `_shared/device-core.ts`: `checkRateLimit` стаў асінхронным і чакае
  атамарны інкрэмент перад параўнаннем з лімітам; лічыльнік з базы
  правяраецца як карэктнае цэлае ≥ 0, інакш рашэнне кідае памылку (адзін
  агульны алгарытм для абодвух endpoint, спец N1 — без асобнага несумяшчальнага
  алгарытму). `RateStorage.increment` цяпер дапускае `number | Promise<number>`.
- Новы `_shared/device-wire.ts`: сапраўдны апрацоўшчык `handleDeviceRequest`
  перанесены з `device/index.ts` (index застаўся чыстай Deno-абвязкай).
  Адаптэр інкрэменту вяртае «сырую» клетку `attempts` без маўклівага значэння;
  унутраныя адмовы адказваюць існымі закрытымі кодамі і даюць роўна адзін
  дыягностык (`device_registration` + `rate_increment_failed` /
  `device_insert_failed`).
- Новы `_shared/events-wire.ts`: сапраўдны wire-апрацоўшчык
  `handleEventsWireRequest` перанесены з `events/index.ts`; catch мапіць адмову
  порта на `500 server_error` + адзін дыягностык (`events_intake` +
  `storage_failure`), як і належыць па кантракце ядра, што не ловіць адмовы
  порта. Табліца падзей перадаецца параметрам, JSON-імпарт застаўся ў Deno-файле.
- `_shared/events-core.ts`: `handleEventsRequest` чакае `checkRateLimit`;
  порт `createSqlEventsPort.incrementEventRate` вяртае «сырую» клетку —
  ранейшы `Number(rows[0]?.['attempts'] ?? 0)` пераўтвараў адсутны радок у
  маўклівы allow.
- Новы `_shared/server-diagnostics.ts`: адзін канал серверных дыягностык —
  адзін радок `{operation, reason}` у stderr, толькі фіксаваныя літаралы.
- Тэсты: новыя `_shared/device-wire.test.ts` (9 тэстаў) і
  `_shared/events-wire.test.ts` (7), агульныя дапаможнікі
  `_shared/wire-test-support.ts`; `device-core.test.ts` пераведзены на await
  і дапоўнены core-тэстамі (асінхронны інкрэмент, несапраўдны лічыльнік);
  `events-core.test.ts` — агульныя фікстуры + рэгрэсія адсутнага радка лічыльніка.

## Па крытэрах

1. **Сапраўдныя апрацоўшчыкі з асінхронным SQL.** `handleDeviceRequest` і
   `handleEventsWireRequest` — тыя самыя функцыі, якія выклікае `Deno.serve`;
   перанесеныя ў `_shared`, каб node-сюіты вадзілі іх скрозь асінхронны
   SQL-фейк (працэдэнт G08.01/G09.02: абвязка на Supabase runtime, кантракт
   у node-тэстах). Першая рэгістрацыя → `201` з `device_id`/`device_secret`,
   роўна адзін rate-інкрэмент і адзін insert; першы батч → `200 {"accepted":1}`,
   батч запісаны адзін раз. Тэсты: «criterion 1: the first registration
   succeeds through asynchronous SQL», «criterion 1: the first event batch is
   inserted exactly once through asynchronous SQL».
2. **Мяжа ліміту і адмовы SQL.** 20-ы/21-ы запыт device і 60-ы/61-ы батч
   events праз сапраўдныя апрацоўшчыкі: усе да ліміту → `201`/`200`,
   наступны → `429` з `retry-after`, без запісу. Несапраўдныя адказанні
   (`undefined`, `null`, `'-радок'`, `-1`, `NaN`, `1.5`, адсутны радок) і
   зламаны SQL (lookup, інкрэмент, insert) → `500 server_error`, нічога не
   запісваецца, ніколі не выдаецца за перавышэнне ліміту. Тэсты: «criterion 2:
   the limit boundary…», «criterion 2: an invalid SQL counter reply fails
   closed…», «criterion 2: a failed SQL reply fails closed…», плюс core-тэст
   «spec N1: a rate reply without a valid counter rejects…».
3. **Адзін атамарны інкрэмент на запыт.** Канкурэнтныя запыты (`Promise.all`,
   ліміт+1) даюць роўна ліміт+1 SQL-інкрэментаў і ліміт запісаў; фейк прымае
   толькі заякарэлачаныя атамарныя сцверджанні (`RATE_INCREMENT_SQL`,
   `EVENT_RATE_INCREMENT_SQL`, `eventInsertSql`) — кліенцкае чытанне-запіс
   гаварыў бы іншым SQL і паў. Тэсты: «criterion 3: one atomic increment per
   request — concurrency never reads-then-writes» у абедзвюх сюітах;
   SQL-канстанты byte-ідэнтычныя (пін у `device-core.test.ts` не змяніўся).
4. **Падзенне на реверце, стандартны runner.** Тэсты ідуць праз `npm test`
   (глоб `"supabase/**/*.test.ts"`, проводка не мянялася) і выкарыстоўваюць
   толькі асінхронны SQL: фейкавы інкрэмент адказвае Promise пасля сапраўднага
   `await`; сінхроннага лічыльніка-фейка ў рэгрэсіях няма. Рэверт-эксперымент:
   выдаленне `await storage.increment` з агульнага рашэння рабіць абедзве
   рэгрэсіі чырвонымі (11 з 16), аднаўленне з git — зелёнае (16/16); каманда і
   вывад — у [дэме](../../demos/2026-10-02-g2001-async-rate-counter.md).
5. **Дзеразны серверны журнал.** Кожны ўнутраны шлях (неўдалы інкрэмент,
   неўдалы insert, адмова lookup/insert у events, несапраўдны лічыльнік) дае
   роўна адзін радок `{operation, reason}`; існыя кліенцкія коды захаваныя
   (`500 server_error` / `server_configuration_error`). Звычайныя адмовы
   (`404`, `403`, `400`, `429`) не пішуць нічога. Сінтэтычныя маркеры ў
   bearer, `x-forwarded-for`, целе запыту і паведамленні памылкі SQL не
   трапляюць у журнал; SQL-параметры (хэш IP, device_id) у логу адсутныя.
   Тэсты: «criterion 5: an internal failure emits one redacted diagnostic…»,
   «criterion 5: ordinary denials produce no diagnostic» у абедзвюх сюітах.

## Межы і не праверанае

- `Deno.serve`, env-gat і адаптэр postgres.js не выконваюцца ў node — гэтая
  абвязка застаецца за Supabase runtime (прэцэдэнт G08.01/G09.02); тыповая
  праверка entrypoints — асобная задача G20.13 (#484).
- Разгорнуты Supabase і рэальны драйвер не правяраліся; паверхня
  `postgres.Sql.unsafe` мадэлявалася структурна (thenable array-like), сапраўдныя
  SQL-сцверджанні правераныя на PGlite у існых сюітах і пінуюцца тэстам
  канстант.
- Ліміты 20 (device) і 60 (events) — існыя заякарэлачаныя канстанты; перагляд
  велічынь не ўваходзіў у задачу.
