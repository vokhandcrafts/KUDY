# G08.03 — Пакупка і restore ў абедзвюх крамах

**Issue:** [#290](https://github.com/vokhandcrafts/KUDY/issues/290) · **Галінка:** `zcode/290` · **Статус:** `complete` (кліенцкая сесія пакупкі даказаная тэстамі і дэмай; **sandbox-пакупка/restore на жывых крамах — `blocked-external`**, акаўнты крам яшчэ не створаныя — чалавечы крок [#330](https://github.com/vokhandcrafts/KUDY/issues/330) адкрыты)

## Што зроблена

Кліенцкая сесія пакупкі `services/entitlement/` (мапа `19` §2.3: «RevenueCat SDK + запыт сервернага гранта; не вырашае права сам | сесія пакупкі; restore асобны»): тыпы кантракту (`types.ts`), закрытая мапа памылак RC (`store-error-mapping.ts`), сэрвісныя функцыі `ensureStoreLink` / `purchaseNonConsumable` / `restoreEntitlements` (`service.ts`), фейк-порт (`fake-port.ts`), RC-адаптар (`expo/rc-port.ts` — адзіны runtime-імпарт `react-native-purchases`), дэма. Кананічныя акаркі — `09` §5.1/§5.2 і ADR [G00.03-payment-evidence](../../architecture/decisions/G00.03-payment-evidence.md) §3; вынік G08.02 — серверны бок гранта, гэта задача — кліенцкі бок транзакцый.

### Крытэрый 1 — non-consumable прадукты; адмена/памылка/затрымка — чэсны стан, не «куплена»

- Вынік пакупкі — закрыты саюз `PurchaseOutcome`: `transaction-finished` / `cancelled` / `payment-pending` / `already-owned` / `not-allowed` / `product-unavailable` / `unavailable` / `store-problem{code}` / `executor-error{code}` / `invalid-input` / `unknown`. Ніводны від не ёсць права: `transaction-finished` — факт сесіі крамы, права вырашае толькі серверны грант (`09` §5.1: «Кліент ніколі не сцвярджае, што ён нешта купіў»).
- Закрытая табліца `CATEGORY_BY_CODE` пакрывае **ўсе 36 значэнняў** `PURCHASES_ERROR_CODE` пінаванага `react-native-purchases@10.9.1` (факт правераны ў `node_modules`, не са здагадкі: адмова SDK нясе `code`, а сама SDK правярае адмену па коду, не па дэпрэкатаваным `userCancelled` — `purchases.js:436`). Гард дрэйфу: тэст параўноўвае ключы табліцы са спісам значэнняў enum, скапіраваным з `error-codes.d.ts` пінаванай версіі — абнаўленне SDK без рашэння пра новы код падае суіт.
- Non-consumable — кантракт паверхні: функцыя названая `purchaseNonConsumable`, паверхня ніколі не выклікае consumable-шлях; стварэнне прадуктаў у кансолях крам — праца аператара (метаданыя — G11.04), у рэпазітары гэтага няма і запісана сумленна.
- Валідацыя на мяжы (implementation-rules 14): сапсаваны `productId` (пусты, з прабеламі, з кірыліцай, >200) → `invalid-input` **да** любога выкліку крамы; чужы `productId` у адказе крамы → `unknown` fail-closed; сапсаваны ack → `unknown` з дыягностыкай, без краху.

### Крытэрый 2 — restore на новай прыладзе той самай крамы

- `restoreEntitlements()` — асобны ўваход (мапа `19`: «restore асобны»): лінкаванне → `store.restore()`. `restore-finished` кажа толькі пра завяршэнне праходу крамы; што ён аднавіў — вырашае грант-шлях, TRANSFER/аліясы разбірае RevenueCat (`09` §5.1). Памылкі restore адказваюць ва ўласным слоўніку (`RestoreOutcome`), катэгорыі з пакупкавай семантыкай → чэсны `store-problem{code}`.

### Крытэрый 3 — няма абяцання cross-platform

- Restore — store-scoped паводле `09` §5.2: «рэстор праз store-акаўнт без рэгістрацыі; перанос між платформамі — Phase 2» (`/v1/link` не ў MVP). Ні тыпы, ні дакументацыя паверхні не маюць крос-платформеннай семантыкі; `types.ts` і `service.ts` фіксуюць гэта тэкстам з акаркамай. Тэксты UI (G08.05) будуць спажываць тыя ж тыпы — заява «права пераносіцца» на гэтай паверхні непрадстаўальная.

### Крытэрый 4 — кожны вынік транзакцыі звязаны з device-акаўнтам праз грант G08.02

- `ensureStoreLink()` ставіць `app_user_id = device_id` (`09` §5.1) — RC `logIn` з UUID, выдадзеным `POST /v1/device` (G08.01); UUID перавяраецца на мяжы праз экспартаваны з `services/device.ts` `UUID_PATTERN` (адзіная копія, без дубля). Паводзіны ідэнтычныя: экспарт канстанты, тэсты G08.01 зялёныя.
- Парадак — частка кантракту: пакупка і restore **адмаўляюцца** без лінку (кароткае замыканне з вынікам лінку); лінк мемарызаваны на порт + deviceId, чужы deviceId пера-лінкуе ўліковы запіс, няўдалы лінк не мемарызуецца. Грант-канец (`/v1/grant` з `Bearer device_secret`, G08.02) атрымлівае тыя ж device-факты — прывязка выніку транзакцыі да акаўнта прылады адбываецца з абодвух бакоў.

## Рашэнні, за якімі варта сачыць наступніку

1. **Пін `react-native-purchases@10.9.1`** — факты адаптара і спіс кодаў табліцы звязаныя з гэтай версіяй; абнаўленне SDK павінна прайсці coverage-гвард (`store-error-mapping.test.ts`).
2. **`executor-error` — дэфект дадатку, не адказ карыстальніку** (`11` invalid-credentials, `14` invalid-app-user, астатнія канфігурацыйныя) — той самы сэнс, што ў `invalid_request` гранта (`19` §3.6). G08.05 не павінен паказваць яго як збой крамы.
3. **`already-owned`** асобны від: крама сама кажа «не бярэм грошай другі раз» — падмурак для G08.04 («купленае не прапануецца купіць зноў»).
4. **CustomerInfo не чытаецца** ні ў фейку, ні ў адаптары: entitlements з яго — не крыніца праўды кліента (`09` §5.1); адзіны спажывец правоў — грант-шлях (G08.04).
5. **Адхіленне ад мапы 19 §2.3**: радок плануе «клас» і файл `services/entitlement.ts`; рэалізаваныя функцыі ў тэчцы `services/entitlement/` — па прэцэдэнце `services/device.ts` (таксама «функцыі» супраць плана), бо ў модуля няма per-instance жыццёвага цыклу, а мемарызацыя — WeakMap на порце. Структура тэчак ужо так жыве для download/location/audio.
6. **Заглушка верыфікацыі не стваралася** — строгі env-гейт ADR §3.7 датычыцца сервернага боку; кліенцкі код ніякіх мокаў праўды не мае.

## Самарэвю (не незалежнае)

Scope: `git diff` — 9 новых файлаў `services/entitlement/**` + 4-радковы экспарт у `services/device.ts` + дэма + гэты result; чужых файлаў не тыкаўся (worktree ад `origin/main`). Primary concern — contract conformance: віды вынікаў і дыягностыкі маюць адзін крыніцу (`store-error-mapping.ts`), акаркі `09` §5.1/§5.2 скапіяваныя даслоўна, «куплена» як сцяг кліента на паверхні не існуе. Сакрэтаў няма: сінтэтычныя UUID/прадукт у дэме, ніякіх ключоў (hygiene). `as`-casts — толькі на мяжы фейка/адаптара (`unknown` → ack), без хавання неадпаведнасцей; `strict` трымаецца. Тэсты дасягаюць прадакшн-шляху: `purchaseNonConsumable` → рэальны мапінг → фейк-порт крамы; нікакой дапаможнай апрацоўкі ўводу, якой няма ў прадакшне. Негатывы: кожнае правіла мяжы (device-id, product-id, ack-shapes, коды) мае тэст, што падае пры яго зняцці (два revert-эксперыменты вышэй). Моўны grep правіла 12 па даданым бе-тэксце — чыста.
