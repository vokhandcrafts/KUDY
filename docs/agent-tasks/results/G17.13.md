- What: the `/records` page in the read-only collector dispatcher — a table of
  every record of every campaign (title from the search index's latest cleaned
  document, URL fallback; source, status, rights with the canonical key next to
  a Belarusian display word; city, collection date, photo and link counts) with
  `?status=` / `?city=` URL filters, a filter bar whose links carry the full
  state (shareable view), and every row linking to the future record card
  (`/record?id=…`, task 06). The page shares the new `pageShell` with the
  overview (nav links, single style block); the empty-store sentence is one
  shared constant. The dispatcher connection is read-only, so the search index
  is read as-is (never re-synced) — a record without a cleaned version falls
  back to its URL, like the CLI's search output.

## Proven (criteria of issue #370)

1. **Table: title, source, status, rights, collection date, photo and link
   counts** — one query over `raw_records LEFT JOIN cleaned_fts` with the two
   counts as scalar subqueries; demo block 1 prints the three fixture rows
   (`docs/demos/2026-09-29-g1713-dispatcher-records.md`), e.g. the raw row
   `… навіны (news) сыравіна (raw) толькі даследаванне (research_only) gdansk
   … 1 2` (1 photo, 2 links). Dispatcher test «records page lists every
   record with counts, rights and the card link» asserts the same fragments.
   A record's city is its campaign's city, so the city filter is the axis
   separating campaigns — the same one the CLI search offers.
2. **Status and city filters via URL; unknown parameter — readable answer
   with a reason, not 500** — `parseRecordFilters` accepts only the two known
   names; an unknown name or an unknown status value renders a named note
   (`class="note"`) and the unfiltered list (status 200); an unknown city
   renders the empty result with a reason; a hostile status value arrives
   escaped (`?status=%3Cscript%3E` renders `«&lt;script&gt;»`, never
   `<script>`). Demo block 2 prints all three situations. The bar's links
   preserve the other parameter — test asserts
   `href="/records?status=cleaned&amp;city=gdansk" class="on"`.
3. **Every row is a shareable link to the record card (task 06)** — the title
   cell is `<a href="/record?id=<id>">`; asserted by id in the tests. The card
   route is deliberately not built here (task 06, #371 — sequential on
   purpose); until it lands the generic 404 diagnostic answers.
4. **Tests: fetch the list against a fixture DB, working filter, unknown
   parameter; red on revert** — `tools/collector/dispatcher.test.mjs` boots
   the real server over the production store fixture (three new tests +
   the extended missing-DB test; fixture gained links, a `cleaned_fts` title
   row and the krakow city on the c2 record). Red-on-revert ran in the
   shipping session: dropping the `/records` route fails 4 tests; disabling
   the status validation fails the unknown-status test; restoring → 12/12.
