## Крытэрый 1 — не больш за 256 прачытаных радкоў да першай адпраўкі і ў кожнай наступнай

Новы выпадак `flush_reads_one_bounded_page_before_send` (20 000 падзей): лічыльнік радкоў праз абгортку драйвера мерае, колькі SELECT аддае чаргі. На да-зменным кодзе чырвоны:

```
AssertionError: the first send attempt must be preceded by at most 256 selected rows, got 20000
```

стары код чытаў увесь неадпраўлены хвост адным запытам і рэзаў па 256 ўжо ў памяці. Пасля змены: першае чытанне 256 радкоў, усе наступныя ≤ 256, 79 старонак, 20 000/20 000 пазначана.

## Крытэрый 2 — знімак enqueue_seq выключае падзеі, дададзеныя падчас флашу

- `backdated_insert_waits_for_next_flush`: падзея з ранейшым `at`, устаўленая ў send-звароце, не трапляе ў бягучы флаш; наступны флаш бярэ яе першай. Параўнальна са старым кодам гэта тэст-гард: стары чытаў усё да цыкла і выключаў навасёлаў выпадкова — цяпер выключэнне кантрактнае, праз замарожаную мяжу ключа.
- `enqueue_seq survives account clearing and reopen, and keeps rising` (file-backed): `clearDeviceAccountState` не скідвае лічыльнік; паўторнае адкрыццё працягвае зрост; ключы монатонныя.
- `an old file-backed store upgrades in place`: сховішча версіі 2 (крокі 1–2) з чатырма радкамі v2-формы (tie па `at`, па-за парадкам, адзін sent) мігруе на месцы: user_version 2→3, backfill у дыспетчарным парадку (evt-o1→1, evt-o2→2, evt-o2b→3, evt-o3→4), лічыльнік працягвае з 5; sent-радок атрымлівае ключ, але застаецца па-за pending.
- Сыры `rowid` не выкарыстоўваецца: лічыльнік — асобная zone B singleton-табліца `event_queue_seq` (адзін радок, `next`), створаная ўнутры кроку 3 па прэцэдэнце кроку 2 (DDL кроку, не пачатковы). Свядома НЕ ў `settings` — інвентар наладаў там клічацца wipe-тэстамі G09.03; пратэставана заменай падыходу ў выкананні (першы варыянт у `settings` ламаў 5 G09.03-выпадкаў).

## Крытэрый 3 — збой другой старонкі захоўвае хвост

`batch_failure_preserves_pending_tail`: send кідае на другой старонцы → першыя 256 пазначаныя, 344 pending у тым жа парадку; паўтор дасылае роўна той хвост тымі ж event_id. Існыя выпадкі G09.01 (крытэрыі 1–5) застаюцца зялёнымі без рэдагавання.

## Крытэрый 4 — згода і ўладальнік паміж старонкамі

- Перад кожнай старонкай: `beforeBatch` (згода — кантракт G09.02 захаваны, існы гейт-тэст зялёны) + пераправерка ўладальніка: `getDeviceId` супраць захопленага на старце флашу.
- `owner_change_stops_old_flush`: замена прылады БЕЗ выціркання чаргі ў сярэдзіне send — флаш спыняецца, marked = 0, 601 pending (нічога не пазначана і не страчана). Зваротны эксперымент: без пераверак выпадак чырвоны (sends = 3, marked = 600) — пераверка цягавая.
- `account_clearing_mid_flush_keeps_the_replacement_event_pending`: `clearDeviceAccountState` + замена падчас send — наступнай адпраўкі няма; падзея новага ўладальніка чакае свайго флашу і дасылаецца ім.
- Пераправерка пасля awaited send перад пазнакай — другі кантрольны пункт цыкла.

## Крытэрый 5 — план запыту і міграцыя старога сховішча

- `the bounded pending read plans over the partial index — no full tail read or sort`: SQL сапраўднага старонкавага чытання захопліваецца абгорткай і плануецца VERBATIM: доступ да чаргі толькі праз `event_queue_pending_order`, бяз TEMP B-TREE. SQLite піша абмежаваны індэкс-праход як «SCAN … USING INDEX» — ранняя прыпынка па LIMIT даказваецца лічыльнікам радкоў (крытэрый 1); голае SCAN і сартаванне забароненыя асэрцыямі.
- Частковы індэкс `(at, event_id, enqueue_seq) WHERE sent = 0`. Зваротны эксперымент: зняцце `CREATE INDEX` → выпадак чырвоны.
- Міграцыя file-backed сховішча без страт радкоў — выпадак крытэрыю 2.

## Крытэрый 6 — дыягностыкі замест небяспечных фрагментаў

- `the bounded pending read rejects malformed bounds with a named diagnostic`: сем крывых межаў (limit 0 / −1 / 1.5 / NaN; upToSeq −1 / 1.5 / NaN) → `DbError` з правілам `event-page-invalid` да выканання SQL; карэктныя межы адказваюць звычайна.
- `a broken enqueue_seq counter answers with a named diagnostic`: `next = 0` і выдалены радок лічыльніка → `appendEvent` і `latestEnqueueSeq` кідаюць `event-seq-state-invalid`, не гадаюць.
- Усе значэнні — звязаныя параметры (`enqueue_seq <= ?`, `LIMIT ?`), інтэрпаляцыі няма.
