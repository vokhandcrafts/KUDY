# G20.20 — Compose real device services at the application root

Issue: #491 (эпік #470). Спэца: `docs/specifications/architecture-hardening/verification-integration.md` §V5.
Выканана 2026-10-06, сесія zcode (GLM-5.3-Flash), галінка `zcode/491`, worktree Linux-хоста.

## Што зроблена

Адзін вытворчы камплект сэрвісаў (V5): `app/_layout.tsx` → `controllers/deviceRoot.ts`
(адзіная expo-прывязка фасілітасаў) → `controllers/deviceServices.ts` (кампазіцыйны
корань: адзін SqlDriver, адна bundles-тэчка, адзін teardown) →
`controllers/createServices.ts` (кампазітар `Services` без зменаў кантракту, плюс
новы неабавязковы порт `readinessFor`). DB-правядка парт (сесіі/падказкі/гісторыя/
нлады/постаянства мовы) перанесена з тэставага віртуальнага свету ў вытворчы
`controllers/sessionPorts.ts`; пін-парт перанесены з `createServices.ts` даслоўна
(адзін уладальнік правілаў піна — ADR G01.03 §3.4).

### Новыя вытворчыя адаптары (усе — чыстыя фабрыкі з ін'екцыяй платформавых аб'ектаў; expo-імпарты толькі ў `app/_layout.tsx`/`controllers/deviceRoot.ts`)

| Адаптар | Файл | Порт |
|---|---|---|
| SQLite-драйвер | `services/db/expo/expo-sqlite-driver.ts` | `SqlDriver` (expo-sqlite ~16.0.10) |
| Дайджэст + UUID | `services/device-crypto.ts` | `Sha256`, ідэнтыфікатар сесіі (expo-crypto ~15.0.9) |
| Файлавыя сторы | `services/contentRepo/expo/expo-package-store.ts` | `PackageStore`, `BundlesStore`, тэйзэр-проба (expo-file-system ~19.0.24) |
| Download-стор | `services/download/expo/expo-download-store.ts` | `DownloadStore` (той самы bundles-корань) |
| Байт-крыніца | `services/download/origin-bytes.ts` | `FetchPort` над публічным origin (`bundle/`), дэдлайн `wait-bundle-bytes` |
| Wakelock | `services/device-wakelock.ts` | структурна `RunWakelock` (expo-keep-awake ~15.0.8, тэг `kudy-run`) |
| Купля недаступная | `services/entitlement/unavailable-port.ts` | `CommercePort`: `stateOf→'not-owned'`, `purchase→{kind:'unavailable'}`, нуль выклікаў крамы |

`package.json`: даданы `expo-file-system`, `expo-sqlite`, `expo-crypto`,
`expo-keep-awake`; у `app.json` — plugin `expo-sqlite` (яго дадаў `expo install`).

### Кампазіцыйныя рашэнні (межы змены)

- `app/` не імпартуе `services/` (правіла `app-no-services`): expo-прывязка жыве ў
  `controllers/deviceRoot.ts`; працоўны прыём — ленівы `require` унутры
  `createDeviceServiceSet()` пры наяўнасці `EXPO_PUBLIC_CATALOG_ORIGIN`, інакш карань
  перадае пусты набор партоў (шчыра недаступныя экраны). Без гэтага render-тэсты
  jest цягнуць expo-модулі, якія не ініцыялізуюцца па-за натыўным рантаймам.
- Канон 19 §2.2 + машыннае правіла `controllers-services-type-only`: тры дадатковыя
  кампазіцыйныя карані (`sessionPorts`, `deviceServices`, `deviceRoot`) дазволена
  value-імпартаваць `services/` — абнаўленне датаванае, базавая лінія арх-гейту не
  пашыраная (`arch:check: OK — 557 modules, 0 violations`).
- Start-брама (`readinessFor`): `RunSessionPorts.readiness` не мае аргументу маршруту,
  таму кампазіцыя стварае пер-маршрутную браму праз новы порт `ServicePorts.readinessFor`
  (пер-маршрутнае перазначэнне ў `run.create`; без порта — старая паводзіна).
  Вердыкт — над `readLayerFacts` (дыскавая праўда прылады: lock пласта + наяўнасць
  файлаў), base granted па ўласным правіле кантракту, extended — толькі з грантам.
- Загрузка: lock адносіцца да layers-каталога на origin (`bundle/…`), на прыладзе
  ляжыць у `bundles/…`; кампазіцыя запісвае сцягнуты `lock.json` побач з файламі —
  інвентарызацыя і Start-брама верыфікуюць супраць таго ж дакумента.
- Выяўлены і зачынены канфлікт разметкі: пусты `staging`-падкорань пасля загрузкі
  рабіў адзіную версію «неадназначнай» для піна — `resolveFreshIdentity` і пін
  фільтруюць вызерваванае імя `STAGING` (уласнік разметкі — `services/download/download.ts`).

### Што наўмысна адсутнічае (шчырая недаступнасць, V5)

`packageStore` (адзіны стор без кантэксту маршруту — прэв'ю ідзе праз `evaluateLayer`…
апошні таксама выключаны: `evaluatePackage` чакае root-файлы пакета, якіх канал
загрузкі не піша; вынікі — у рэзюмэ ніжэй), `runSession`/`walk` (патрэбен join назвы
маршруту з праекцыяй каталога), `discoverySnapshot`/`discoveryAnalytics`,
`guideHints` ( няма дакумента значэнняў на прыладзе), `feedback` (патрэбен functions
origin). Купля/restore — яўна недаступны парт да G20.21 (нуль store/grant/paid-byte
выклікаў па пабудове: `react-native-purchases` не імпартуецца; гард у wiring-тэсце).

## Доказы па крытэрыях

1. **Інвентарызацыя** — праведзена (гл. каментар клейму ў issue #491 і табліцу вышэй);
   рэалізаваны толькі патрэбныя для бясплатнага цыклу адаптары; адзін уладальнік
   DB/аўдыё/GPS + яўны `teardown()` (wakelock lease; корань вештае яго на unmount).
2. **Корань спажывае кампазіцыю** — `app/_layout.tsx` не імпартуе `services/` і `core/`
   прама; `arch:check` зелёны (557 модуляў, 0 парушэнняў, базавая лінія ад 2026-10-02
   не пашыраная). Гард wiring `controllers/wiring.test.ts` пашыраны двума праверкамі:
   кампазіцыйныя карані `deviceRoot.ts`/`deviceServices.ts` не імпартуюць крамавую
   сесію (кветкаваны module specifier), а `_layout` кампазіцыю выклікае і чытае
   `EXPO_PUBLIC_CATALOG_ORIGIN`. Брама паходжання — чыстая `catalogOriginFrom()`
   ў `deviceServices.ts`, тэст інтэграцыі правярае яе паводзіну (null/значэнне).
3. **Бясплатны сінтэтычны пакет** — інтэграцыйны тэст
   `controllers/deviceServices.integration.test.ts` праходзіць каталог →
   загрузка/хэш/актывацыя → Start (Active) → Pause (радок `paused`, wakelock release) →
   restart (аднаўленне праз recovery-порт, фаза `Paused`) → End (радок завершаны,
   жывога чытання няма); купля — `{kind:'unavailable'}`; пераключэнне мовы выжывае
   рестарт праз `settings`-радок. Фейкі толькі на мяжы Expo/OS (V1).
4. **Адсутнасць канфігурацыі/збоі адаптараў** — без `EXPO_PUBLIC_CATALOG_ORIGIN` корань
   перадае пусты набор партоў (тэст «without a catalog origin…»); lock/файлавыя збоі
   даюць іменаваныя дыягностыкі (`download-lock#unreadable`, `bundle-bytes#status-N`,
   `expo-sqlite-driver#bigint-param`), бяспечныя прычыны `preview#…` рэндзяцца
   існымі лакалізаванымі радкамі; новыя радкі не патрэбныя.

## Межы і прыклады для #296 (не прэтэндую на жывую прыёмку)

- Натыўны рантайм не прагнаны: ўсе expo-модулі ў тэстах стаяць на мяжы Expo/OS;
  першы жывы прагон патрабуе `expo prebuild -p android` + зборкі dev-client на
  main з гэтымі залежнасцямі (гл. памяць device run: перазборка пасля новых
  натыўных модуляў абавязковая).
- iOS/фізічная прылада, жывы origin з рэальным каталогам, sandbox-аплата — па-за
  гэтай задачай (G20.21/#296/#297).
- Windows: запісы ў гэтых выніках зроблены на Linux-хосце; экспарцёртныя шляхі
  (`'/'`-размяжоўнікі ў `rel`) — той самы ідыём, што і ў node-стораў.
- Экспанентны драйвер рыхтуе заяву на кожны run/get/all без кэшу выказванняў
  (гарачы шлях checkpoint'аў рыхтуе тую ж SQL зноў). На прыладзе не вымерана;
  кэш падготовленых выказванняў — свядома адкладзенае ўдасканаленне, не дэфект
  карэктнасці (кожны выклік фіналізуе заяву — без накоплення натыўных стэнтографаў).

## Парушаныя прыёмкі / адхіленні ад літары крытэраў

- Крытэр 3 («праз вытворчую кампазіцыю») выкананы на node:sqlite як стэнд-іне
  Expo/SQL-мяжы: вытворчы драйвер `expo-sqlite` мае ўласныя мапынг-тэсты, але
  рухавік SQLite у тэсце — node:sqlite (той самы `SqlDriver` кантракт).
- `evaluateLayer` выключаны з кампазіцыі (неабавязковы порт): кантракт
  `evaluatePackage` чакае root-файлы пакета (`route.json` у корані), а канал
  загрузкі іх не дастаўляе. Гэта ўзгоднена з V5 («адсутны адаптар мае яўны
  бяспечны стан»); прэв'ю верыфікуе праз інвентарызацыю дыска.
