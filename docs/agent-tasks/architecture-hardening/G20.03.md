# G20.03 — Commit walk transitions before publishing state

## Goal

A storage failure leaves one authoritative durable walk state, visible failure and a retry that can actually persist.

## Sources

- Specification: [runtime.md](../../specifications/architecture-hardening/runtime.md), section R2.
- [Publication index](README.md) contains the real issue IDs and dependencies.
- [Original audit](../../audits/2026-10-02-architecture-review.md) and [reproduction script](../../audits/2026-10-02-proof.mjs.txt).

## Evidence boundary

Audit A26-03: memory Paused, SQLite active; retry leaves pauseWrites=1.

## Scope

controllers/run/runOrchestrator.ts; controllers/useRunController.ts; services/db session paths; transition tests.

## Acceptance criteria

1. [ ] For Pause, Resume, End and progress, inject a write failure against the real local DB path and verify memory/UI never advertise a successfully committed transition.
2. [ ] Pause/End storage failures stop physical audio/autotriggers safely, show failure and keep the last durable state for restart; no automatic audio restart occurs.
3. [ ] Retry persists once storage recovers; restart and rapid ordered actions preserve session identity, progress and version.
4. [ ] The failing-write and retry tests fail on reverting the ordering fix; no cache purge or rollback deletes durable progress.

## Out of scope

No new features, engine rules, access bypasses, unrelated refactoring or production data.
