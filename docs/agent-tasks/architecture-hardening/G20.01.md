# G20.01 — Await SQL rate counters before accepting device and event requests

## Goal

A valid first registration and event batch succeed through asynchronous SQL; exceeding the existing limit returns 429.

## Sources

- Specification: [network-privacy.md](../../specifications/architecture-hardening/network-privacy.md), section N1.
- [Publication index](README.md) contains the real issue IDs and dependencies.
- [Original audit](../../audits/2026-10-02-architecture-review.md) and [reproduction script](../../audits/2026-10-02-proof.mjs.txt).

## Evidence boundary

Device adapter reads db.unsafe as rows; events-core.ts:390: passes Promise<number> to a synchronous comparison. Reproduction: attempts=1 -> 429 event_rate_limited, inserted=false.

## Scope

supabase/functions/device/index.ts; supabase/functions/events/index.ts; _shared/device-core.ts; _shared/events-core.ts; handler/SQL and server-log tests.

## Acceptance criteria

1. [ ] Invoke the production device handler and event handler with asynchronous SQL responses: the first request succeeds and the event batch is inserted once.
2. [ ] The limit boundary and one request beyond it retain the existing 429/retry contract; invalid or failed SQL replies fail closed without inserts.
3. [ ] Keep one atomic increment per request; concurrent requests cannot replace atomic SQL with a client-side read/update.
4. [ ] Both regressions fail when awaiting the SQL result is removed; the tests run through npm test and do not use a synchronous counter fake.
5. [ ] Production device/events internal failure paths emit one redacted server diagnostic with operation/reason, retain existing client error codes, and never log body, bearer, SQL parameters or connection URL. Capture real handler logs with synthetic secret markers; missing logging and unsafe logging each fail the check.

No new features, engine rules, access bypasses, unrelated refactoring or production data.
