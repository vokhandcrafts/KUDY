# G20.26 — Limit grant requests before consuming the entitlement provider budget

## Goal

One authenticated device cannot send unlimited RevenueCat verification requests; limiter faults deny safely and quota rejection has bounded client retries.

## Sources

- Specification: [network-privacy.md](../../specifications/architecture-hardening/network-privacy.md), section N8.
- [Task index](README.md) and [review boundary proof](../../audits/2026-10-02-review-boundaries-proof.mjs.txt).

## Evidence boundary

handleGrantRequest authenticates then calls handleGrant; no grant rate gate precedes the provider verifyEntitlement path. Provider quota exhaustion itself has not been tested live.

## Scope

supabase/functions/grant/index.ts; atomic server rate storage/migration; grant client response/retry contract; canonical09 changes if needed.

## Acceptance criteria

1. [ ] Use an atomic authenticated-device counter before the provider call; a finite window/burst config has one owner, and missing/bad config or storage failure never bypasses the gate.
2. [ ] Record configured per-device limits and aggregate provider-budget protection from verified deployment quota data without inventing a provider quota; preserve cache/environment isolation.
3. [ ] At and beyond the limit, assert bounded attempts and zero additional provider calls. A second device works within the total budget; concurrency and retry cannot bypass counting.
4. [ ] Keep response codes in the canonical closed contract: introduce 429/retry behavior there and in the client parser if needed in the same task. Behavioral tests fail on gate removal; any migration keeps RLS and a rollback/recovery note.

## Out of scope

New product features, weakening authorization, live secrets, unrelated cleanup, dispatcher/branch-protection changes and implementation before publication.
