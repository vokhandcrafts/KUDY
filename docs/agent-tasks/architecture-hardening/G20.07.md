# G20.07 — Keep foreground location when background permission is denied

## Goal

Foreground and background capabilities are represented independently; background denial cannot revoke an existing foreground grant.

## Sources

- Specification: [runtime.md](../../specifications/architecture-hardening/runtime.md), section R4.
- [Publication index](README.md) contains the real issue IDs and dependencies.
- [Original audit](../../audits/2026-10-02-architecture-review.md) and [reproduction script](../../audits/2026-10-02-proof.mjs.txt).

## Evidence boundary

Code evidence: expo-location-port.ts:98 maps either request into the same permissionState. No device proof of until-restart behavior.

## Scope

services/location/expo/expo-location-port.ts; permission-mapping.ts; services/location/service.ts; location UI mapping if needed.

## Acceptance criteria

1. [ ] Using the real adapter/service, grant foreground then deny background: foreground fixes remain available while background updates are not requested.
2. [ ] Deny both scopes: no watcher starts and the existing user-visible permission state remains accurate.
3. [ ] Mode changes, permission responses arriving out of order and explicit retry cannot overwrite a newer capability decision.
4. [ ] Tests prove scope behavior and fail on merging the permission states; Android/iOS dialog behavior remains explicitly unverified until device acceptance.
