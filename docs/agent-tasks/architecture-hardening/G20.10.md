# G20.10 — Bound catalog configuration device and package network waits

## Goal

A stalled request terminates, uses a verified cache or safe failure and releases its timer and owner.

## Sources

- Specification: [network-privacy.md](../../specifications/architecture-hardening/network-privacy.md), section N4.
- [Publication index](README.md) contains the real issue IDs and dependencies.
- [Original audit](../../audits/2026-10-02-architecture-review.md) and [reproduction script](../../audits/2026-10-02-proof.mjs.txt).

## Evidence boundary

Current fetch calls in loader.ts, remote-config.ts and device.ts have no request deadline. GrantFetchDeps.fetchBytes and lock_url byte downloads in services/download/grant.ts also lack a bounded wait.

## Scope

services/catalog/loader.ts; catalogService.ts; services/remote-config.ts; services/device.ts; services/download/grant.ts; download activation/cancellation and timeout tests.

## Acceptance criteria

1. [ ] With controlled clock and an unresolved fetch, catalog falls back to a validated disk copy by the configured deadline; without a copy it surfaces existing failure.
2. [ ] Remote config retains existing safe defaults; failed registration does not persist a fabricated secret or identity.
3. [ ] Owner disposal aborts the request; timers/listeners are cleaned after success, timeout and cancellation; late replies cannot mutate disposed state.
4. [ ] Choose and record one timeout-policy owner after searching existing helpers; tests run in npm test and fail on removing deadlines.
5. [ ] An unresolved grant/lock/media fetchBytes or response-body read terminates at its deadline, cleans abort/timers and leaves no incomplete-ready package. Cancellation cannot accept a late reply; verified files remain resumable and the UI gets a named failure. Removing the byte-transfer deadline fails the standard check.

## Out of scope

No new features, engine rules, access bypasses, unrelated refactoring or production data.
