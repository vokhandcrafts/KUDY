# G06.10.f — Live walk progress

**Status:** not-started. **Model class:** medium. **Dependencies:** G06.10.a closed. Parent task: G06.10 ([16 design block](../../16_delivery_backlog.md)).

## Scope

The walk progress stops being a jumping width number: the 6px fill of the Run bar (and any progress figure shown with it) moves as a living line — the fill eases to a new value and a figure cross-fades when it changes. The founder approved exactly this pattern; the other animation patterns are consciously out of scope. The whole thing respects the reduce-motion setting: with "less motion" on, values land instantly without transitions (canon §9).

Read: [visual-language.md](../../design/visual-language.md) §5 (Run panel, progress 6px), §9 (reduced motion), the parent [G06.10.md](G06.10.md), the current Run bar implementation and its tests, [implementation-rules](../../agent-rules/implementation-rules.md). Dependency note: the animation base is pinned to the SDK 54 line (reanimated ~4.1.x + its worklets peer — install through `npx expo install`, record the pins).

## Allowed outputs

- `package.json` + `package-lock.json` — the animation base pinned via expo install for SDK 54
- one progress component in `components/` (fill + optional figure, both token-colored) with reduce-motion handled by the animation base's system-aware mode
- the Run bar surface consuming it (the strip whose fill currently jumps by percent width); its existing tests keep passing with final-state assertions
- tests: with reduce-motion on, a progress change lands at the final width without any transition; with motion allowed, the animated properties are present (fill eases, figure fades); `docs/demos/<YYYY-MM-DD>-g0610f-progress.md`, `docs/agent-tasks/results/G06.10.f.md`

## Acceptance

1. [ ] The Run bar fill eases to each new progress value (no percent-width jumps) and the figure, where shown, cross-fades; a render test asserts the animated component is mounted with the 6px track and token colors.
2. [ ] With the reduce-motion setting on (mocked in tests), a progress change applies the final width immediately — no transition values present; with it off, the animation configuration is present. Both paths are covered by tests.
3. [ ] The existing Run behavior stays green: the bar still belongs to the audible story, marker and panel contracts untouched; `app/run` tests pass with final-state assertions.
4. [ ] Dependency pins are recorded with their source (ADR G00.04 §6 style note in the results); `npx expo-doctor` passes.
5. [ ] `npm test`, `npm run typecheck`, `npm run arch:check` and the copy-paste gate are green.

## Out of scope

Every other animation pattern (content fade-up, stagger, dragon spring, marker pulse, dialog animation, shimmer, count-up — consciously skipped in the founder quiz); map marker animation; the web/; animating anything except walk progress.

## Proof

Point the fill back to the static percent-width style (or strip the reduce-motion branch) → the corresponding test fails; restore → green. Showboat: required (user-visible runtime behaviour — a recorded progress change in both motion modes).
