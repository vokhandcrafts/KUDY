# G22.03 — Read analytics events in bounded acknowledged batches

Draft implementation plan. Publication and execution require the review described in [README](README.md).

> For agentic workers: use `superpowers:executing-plans` for the approved plan. Current checkout only.

## Goal and scope

The first send and every later batch read at most 256 pending rows while preserving consent, account ownership, stable order and retry identity.

- [Specification E3](../../specifications/efficiency/2026-10-04-bounded-work.md#e3-абмежаванае-чытанне-чаргі-падзей--g2203).
- Modify `services/db/db.ts`, the owning migration/schema steps in `services/db/schema.ts`, and `services/eventLog.ts`.
- Tests: `services/db/db.test.ts`, `services/eventLog.test.ts` and existing consent/device-owner behavior suites.

## Interfaces and acceptance criteria

Preserve `flushEvents` and its per-batch `beforeBatch` gate. Make the pending read accept a bounded page and insertion snapshot through the existing DB owner; update actual consumers together. Do not create a sibling full-queue implementation or duplicate the batch constant.

Use an explicit durable, monotonically increasing `enqueue_seq` insertion key; migrate existing rows and allocate new values transactionally through the DB owner. Its counter is not reset by `clearDeviceAccountState`. Plain SQLite `rowid` is not a safe snapshot key: deleted row numbers can be reused after account clearing. Recheck captured account ownership before sending and after the awaited send, before acknowledging.

1. [ ] A real SQLite queue with 20,000 pending events produces at most 256 selected rows before the first send attempt and at most 256 per subsequent query.
2. [ ] Stable `at, event_id` ordering and the `enqueue_seq` snapshot exclude events added during the flush, including backdated events and rows inserted after account clearing. They remain pending for the next flush; reopen and clearing never reuse the insertion sequence.
3. [ ] Failure on batch two leaves batch one acknowledged and all unacknowledged events pending; retry/reopen keeps original event IDs.
4. [ ] Consent revoked between batches prevents the next send. Account deletion/replacement prevents old work from acknowledging events of the replacement account.
5. [ ] The real query plan uses an appropriate index without a full pending-tail read/sort. Upgrade an existing file-backed DB without deleting rows or breaking replay.
6. [ ] Malformed page/cursor state produces a named DB diagnostic rather than an unsafe SQL fragment; SQL values are bound parameters.
