## Goal and scope

My KUDY can load completed history in bounded pages without hiding the live walk or modifying stored progress.

- Tests: `services/db/db.test.ts`, `controllers/myKudyController.test.ts`, `app/my.test.tsx`.

## Interfaces and acceptance criteria

The DB owner defines `SessionHistoryCursor` from `startedAt` and `sessionId`, and a `SessionHistorySummary` with the existing identity/state/timing fields plus derived `heardCount`. These are projections, not new stored progress. The port provides `listPage(cursor: SessionHistoryCursor | null): Promise<SessionHistoryPage>`; a page contains `live`, completed `rows`, and `nextCursor`. Page size is 50. Update root/controller/UI consumers together; full session reads remain available for actual progress use.

1. [ ] Compare read/render work on 20, 100 and 500 synthetic sessions and label these as measurements, not user-frequency claims.
2. [ ] A page reads at most 50 completed summaries in `started_at DESC, session_id DESC` order. No all-history progress-array load or offset traversal is hidden in summary calculation.
3. [ ] The live active/paused session is available separately and remains visible while paging completed sessions.
4. [ ] Tied times, new completion between pages, refresh versus late load-more, and final empty pages do not lose, duplicate or restore stale rows.
5. [ ] Use React Native `FlatList` with stable IDs and existing header/language controls. Do not put another complete-history map inside a row/header.
6. [ ] Existing stored progress survives the idempotent index migration/reopen unchanged; summary counts match actual session data. Any SQL feature must be supported by the real target driver, not assumed from Node alone.
