# APR-09.a — Дызайн бяспечнага пераносу прагрэсу Android

**Задача:** [#833](https://github.com/vokhandcrafts/KUDY/issues/833). **Аснова:** `main` на `bc7587c0f185c7e85bfb0c0c59f801775469dbdd` (2026-11-01). **Стан:** праект дызайну; рэалізацыя і прыладавыя праверкі не выкананыя. Гэта не дазвол уключаць backup у рэлізе.

## 1. Нязменныя патрабаванні

Прынятае рашэнне — **C** з [APR-09](APR-09-android-backup.md): аднаўляць карыстальніцкі прагрэс, але не пераносіць сакрэт, прыладавую ідэнтычнасць, згоды і сеткавыя чэргі. Зыходная SQLite-база застаецца асноўным сховішчам. Экспарт не можа запускаць GPS, аўдыё, сеткавую адпраўку або аднаўленне пакупкі.

- `controllers/deviceRoot.ts` адкрывае `kudy.db` праз `openDatabaseSync`; `services/db/schema.ts` змяшчае незаменны прагрэс і прывязку прылады **ў адным файле**. Капіяваць `kudy.db` ці яго `-wal`/`-shm` нельга.
- `services/device.ts` можа зарэгістраваць новую прыладу, калі адсутнічае адна частка пары `device_id`/SecureStore. Таму ўсякая рэстаўрацыя старога файла базы да старту рэгістрацыі — асобная пагроза.
- `services/db/db.ts` валодае транзакцыямі (`inTransaction`); `services/db/types.ts` і `schema.ts` — крыніцы дакладных назваў і тыпаў. Ніякіх асобных праекцый SQL-схемы ў UI.
- `controllers/sessionPorts.ts` дазваляе аднавіць толькі валіднае значэнне `ui_locale`. Згода `analytics_consent` належыць `services/analytics.ts`, `crash_consent` — `services/crash.ts`.

## 2. Параўнанне механізмаў

| Падыход | Прагрэс | Рызыка |
| --- | --- | --- |
| Звычайны Android backup усёй SQLite-базы з выключэннем SecureStore | Фармальна можа захавацца | Пераносіць `device`, згоды і чэргі; **адхілены** |
| `allowBackup=false` ці выключэнне ўсіх файлаў | Не захоўваецца | Незваротная страта пасля пераўсталявання; **адхілены ўладальнікам** |
| Пераносны файл па строгім спісе + Android cloud/D2D XML | Захоўвае толькі дазволеныя запісы | Простая праверка файлавага складу; backup можа захапіць састарэлы snapshot пры спыненні працэсу да экспарту; **папярэдні выбар для прататыпа, не release-рашэнне** |
| Уласны Android `BackupAgent.onFullBackup` + `onRestoreFinished` | Можа выбраць санітаваныя даныя на момант фактычнага backup | Натыўная рэалізацыя з доступам да SQLite ў абмежаваным працэсе; не можа спадзявацца на Expo JS, патрабуе `android:fullBackupOnly` і асобнай праверкі абодвух Android XML-рэжымаў |
| Key/value `BackupAgent.onBackup` / `onRestore` | Можа перадаваць асобныя запісы замест файла | Натыўны фармат і міграцыі, `BackupManager.dataChanged()`, квоты і асобная логіка D2D; выклік backup не адбываецца імгненна |

**Ацэнка найменшага бяспечнага механізму:** прапанаваны XML + санітаваны файл не патрабуе асобнага native agent і захоўвае Expo config-plugin кантракт #833. Але страта прамежку паміж SQLite commit, запісам файла і рэальным Android backup не выключаная. Уласны `onFullBackup` можа прыбраць менавіта затрымку экспарту да запуску backup, **але не** адтэрміноўку самога Android backup, а яго native-код павінен безопасна чытаць SQLite без Expo JS і даказаць адсутнасць канкурэнтных запісаў. Key/value backup таксама патрабуе дадатковага натыўнага кода і не гарантуе імгненную копію. Канчатковае рашэнне пасля вымярэнняў і пацверджання рызыкі ўладальнікам (§6), а не маўклівая перамена прынятага варыянту C.

Афіцыйныя падставы: [Android Auto Backup — BackupAgent і абмежаваны працэс](https://developer.android.com/identity/data/autobackup), [Key/value backup — onBackup/onRestore і адкладзены выклік](https://developer.android.com/identity/data/keyvaluebackup), [BackupAgent.onFullBackup](https://developer.android.com/reference/android/app/backup/BackupAgent#onFullBackup(android.app.backup.FullBackupDataOutput)).

Прапанаваны шлях у дамене Android `file`: `files/kudy-portable/progress.v1.json` (адносны шлях `kudy-portable/progress.v1.json`). Гэта **не** `files/SQLite/` і **не** `files/bundles/`. Канчатковую магчымасць бяспечнай атамарнай замены файла трэба пацвердзіць праз рэальны Expo FileSystem. Не капіраваць SQLite, нават у часовую дырэкторыю backup.

## 3. Пераносныя даныя: яўны спіс

**Дазволеныя палі:**

1. `session` — толькі дакладныя калонкі `session_id, route_id, version, locale, audio_locale, tier, state, started_at, finished_at, auto_fired, heard, last_stop_id, play_seq`. Для `active`/`paused` патрэбны асобны неактыўны стан аднаўлення (§4), не аўтазапуск ранейшай прагулкі.
2. `guide_hint_state` — толькі `scope='session'` і запісы, якія адносяцца да пераносных `session_id`: `scope, guide_id, session_id, shown_at, dismissed_at`. Часовае `scope='foreground'` не пераносіць.
3. `guide_hint_last` — `guide_id, last_shown_at, last_dismissed_at`, каб не згубіць ужо паказаныя падказкі.
4. `migration_log` — `version, applied_at, session_id, original_stop_id, story_id, legacy`. Правяраць адпаведнасць перанесеным сесіям; `session_id IS NULL` ацэньваць як асобны агульны запіс, а не выпадкова адкідваць.
5. `settings` — **толькі** `ui_locale` пасля праверкі па `COMPLETE_UI_LOCALES`.

**Забароненыя даныя:** `device`, `device_secret`, увесь SecureStore, `event_queue`, `event_queue_seq`, `feedback_outbox`, `feedback_local`, усе іншыя `settings` (у тым ліку `analytics_consent` і `crash_consent`), `bundle_asset`, `catalog_cache`, `discovery_cache`, файлы `bundles/`, токены і правы на пакупкі. Невядомая новая калонка **не** становіцца пераноснай па змаўчанні.

`feedback_local` у v1 **не пераносіцца** — уключэнне чарнавікоў запатрабуе асобнага выразнага стану «не адпраўляць без дзеяння карыстальніка». На зыходнай прыладзе ўсе чэргі і чарнавікі застаюцца як былі.

**Дадатковыя табліцы не ствараюць новага backup-фармату:** калі існуюць `restore_pending_session`, `restore_pending_guide_hint_state` або `restore_pending_migration_log`, экспарт павінен праецыраваць іх у тыя самыя лагічныя масівы `sessions`, `guideHints`, `migrationLog` з першапачатковымі значэннямі. Нельга выпусціць pending-прагулку з наступнай копіі або аддубляваць яе, калі яна ўжо перанесена ў звычайную `session`. Пры супадзенні ID з рознымі значэннямі экспарт не стварае несупярэчлівы на выгляд файл, а паведамляе памылку.

## 4. Фармат, экспарт і імпарт

- Фармат — версіяваны аб'ект `{format: 'kudy-progress', version: 1, sourceInstallationId, snapshotId, schemaVersion, sessions, guideHints, guideHintLast, migrationLog, settings}`. `sourceInstallationId` — выпадковая пазнака лакальнай устаноўкі, не `device_id` і не сакрэт. Дазволены толькі вядомыя ключы, дакладныя тыпы і межы памеру/колькасці. Невядомая версія або пашкоджаны JSON вяртае дыягностыку без змены SQLite.
- `snapshotId` — устойлівы ідэнтыфікатар зместу для паўторнага імпарту; праверка checksum можа выяўляць пашкоджанне, але **не** з'яўляецца аўтэнтыфікацыяй. Даступ да воблачнай копіі абараняюць сродкі Android, уласнае шыфраванне не ўводзіцца.
- Экспарт чытае дазволеныя радкі **ў адным здымку SQLite** з выкарыстаннем наяўнай транзакцыйнай мяжы. Файл запісваецца спачатку ў часовы шлях у той жа дырэкторыі, затым замяняе кананічны толькі пасля паспяховага поўнага запісу; памылка захоўвае папярэдні прыдатны snapshot. Патрэбны proof фактычнай атамарнасці ў Expo/Android.
- Кандыдат з чужой устаноўкі спачатку **захоўваецца без страты ў асобным каранціне** і праходзіць праверку **без запісаў у БД**, потым у адной транзакцыі ўжываюцца асобныя правілы кожнай табліцы (§4.2). Ні памылка імпарту, ні яго адкладанне не дазваляюць экспарту перапісаць яшчэ не прыняты файл (§4.1). Існыя сесіі не перазапісваць; канфлікт па `session_id` з іншым змесцівам — адмова ўсяму імпарту без знішчэння лакальнага прагрэсу. Журнал ужытага snapshot — у SQLite і ў той жа транзакцыі, без паўторнай адпраўкі дзеянняў.
- Сесіі `finished` аднаўляюцца ў гісторыю. Сесіі `active`/`paused` змяшчаюцца ў **асобную табліцу зоны B** для неактыўных кандыдатаў, не ў новую велічыню `session.state` (§4.3); гэты стан не бачыць `getLiveSession`. Пераўтварэнне ў актыўную сесію дапускаецца толькі па дзеянні карыстальніка пасля праверкі файлаў гіда.
- Адсутныя аўдыё/гіды не пазначаць як гатовыя: існыя `readinessFor` і `bundlesStore` павінны пераправерыць файлы. Імпарт не актывуе GPS/аўдыё/сетку, не выконвае `ensureDeviceIdentity` і не змяняе purchase entitlement.
- Пашкоджанне, збой харчавання, перапыненая транзакцыя або паўтор пасля restart не могуць пакінуць часткова адноўленыя запісы. Запіс у файл і транзакцыя БД — **розныя** межы; патрабуецца асобная праверка кожнага crash-window.

### 4.1. Калі выконваецца экспарт і як распазнаць імпарт

- **Абавязковы парадак запуску:** спачатку каранцін і класіфікацыя адноўленага файла (ніжэй), потым бяспечны імпарт або яўна захаваны адкладзены стан, і **толькі затым** дазвол на першую генерацыю новага export. Не запускаць каардынатар экспарту, рэгістрацыю ці сеткавыя адпраўкі да завяршэння каранціну і асобнага pre-policy gate (§6).
- Пасля **кожнага паспяховага commit**, які змяняе `session` (Start, checkpoint, pause, resume, switch, finish), `guide_hint_state`, `guide_hint_last`, `migration_log` або `ui_locale`, сэрвіс ставіць задачу на абнаўленне пераноснага файла. Фонавы/пярэдні рэжым запускае паўторную спробу для няскончанага экспарту, але Android можа забіць працэс у фоне; адзін `AppState` event не гарантуе захаванне.
- Адзіная серыялізаваная чарга экспарту чытае здымок у SQLite-транзакцыі, аб'ядноўвае запыты і сачыць за нумарам пакалення. Старэйшы асінхронны запіс **не можа** перапісаць навейшы; калі падчас запісу прыйшлі новыя змены, запісаць свежы snapshot яшчэ раз. Выкарыстоўваць часовы файл, поўную праверку і атамарную замену з захаваннем папярэдняга прыдатнага snapshot; фактычную атамарнасць у Expo/Android спачатку праверыць.
- Лакальны маркер `sourceInstallationId` знаходзіцца **толькі** ў Android `noBackupFilesDir` (прапанаваны `kudy-portable-origin.v1`) і не пераносіцца з cloud/D2D. Пераносны файл утрымлівае яго значэнне. **Калі значэнні супадаюць** — гэта ўласны snapshot, у жывую SQLite-базу яго не імпартаваць (ён можа быць састарэлы). **Калі маркер адсутнічае або іншы**, файл — толькі *кандыдат*, а не дазвол на аўтаімпарт: спачатку каранцін і ізаляцыя старой базы (§6).
- **Захаванне адноўленага кандыдата:** перад першым лакальным экспартам перамясціць або бяспечна скапіяваць *арыгінальныя байты* чужога `files/kudy-portable/progress.v1.json` у `noBackupFilesDir/restore-quarantine/<snapshotId>` (унікальная бяспечная назва, без даверу да непацверджанага ID). Запісаць устойлівы запіс пра каранцін, памер і SHA-256, прачытаць файл назад і праверыць супадзенне; толькі пасля гэтага дазволіць экспарт у ранейшы шлях. Пры перапыненым пераносе правяраць **абодва** шляхі і аднаўляць той самы кандыдат, не перазапісваючы ніводную копію. Усе імёны шляхоў праходзяць праверку бяспечных сегментаў.
- Калі каранцін не атрымаўся ці яго цэласнасць не даказаная, **забараніць экспарт**, пакінуць зыходны файл нязменным і паказаць адкладзенае аднаўленне. Пры памылцы праверкі, невядомай версіі, канфлікце або выбары «пазней» каранцін **не** выдаляць і не запускаць аўтаматычную сеткавую адпраўку ад яго імя. Сціраць каранцін можна толькі пасля пацверджанай атамарнай прыёмкі ўсіх запісаў або асобнага свядомага рашэння карыстальніка аб адмове ад аднаўлення. `noBackupFilesDir` сам не пераносіцца далей, таму незавершаны каранцін не абяцае паўторную міжпрыладавую копію.
- Пры першым абнаўленні старога дадатку ранейшага `progress.v1.json` няма; новы маркер можна стварыць толькі пасля бяспечнага bootstrap. Калі старая OS-копія аднавіла ўсю базу без гэтага файла, адрозненне ад звычайнага upgrade застаецца **адкрытым release-gate** (§6); нельга рэгістраваць новую прыладу або адпраўляць старую чаргу да праверкі.
- Android backup возьме **апошні паспяхова запісаны** пераносны файл, а не апошні commit SQLite аўтаматычна. Пры нечаканым закрыцці апошнія змены могуць не трапіць у файл або OS backup; не абяцаць поўнае аднаўленне без фактычных прыладавых доказаў.

### 4.2. Зліццё з існымі лакальнымі данымі

Увесь payload валідуецца перад транзакцыяй. Дублі і канфлікты апрацоўваюцца дэтэрмінавана; пры немагчымасці бяспечнага аб'яднання **ўвесь імпарт адкатваецца**.

| Табліца | Правіла канфлікту |
| --- | --- |
| `session` | Адсутны ID — уставіць; існы з аднолькавымі значэннямі — прапусціць; існы з адрозненнямі — адмовіць без перазапісу. `active`/`paused` ідуць у асобную табліцу (§4.3). |
| `guide_hint_state` | Толькі `scope='session'`. Дзіцячы запіс завершанай або ўжо існай `session` — у звычайную табліцу; для `restore_pending_session` — у `restore_pending_guide_hint_state`, без страты `dismissed_at`. У кожнай праекцыі ключ `(scope, session_id, guide_id)`: ідэнтычны запіс прапусціць, розны — канфлікт з адкатам. |
| `guide_hint_last` | Па `guide_id` узяць максімальныя `last_shown_at` і не-NULL `last_dismissed_at` **паасобку**, каб не скарачаць ужо назапашаны cooldown. Правяраць тыпы часу. |
| `migration_log` | Фізічнага PK няма. Ключ дакладнага дубля — **ўсе шэсць** тыпізаваных палёў `(version, applied_at, session_id, original_stop_id, story_id, legacy)` з асобным маркерам для `NULL`. Для `restore_pending_session` — асобная `restore_pending_migration_log` да актывацыі; `session_id IS NULL` і гісторыя завершаных сесій ідуць у асноўную табліцу. Ідэнтычны дубль прапусціць; пры супадзенні `(version, session_id, original_stop_id)` з рознымі іншымі палямі — адкат усяго імпарту. |
| `settings` | Для `ui_locale` лакальнае значэнне мае прыярытэт **толькі калі яно ўваходзіць у `COMPLETE_UI_LOCALES`**. Адсутны або сапсаваны лакальны код (які `createUiLocalePersistence.read()` ужо трактуе як адсутны выбар) заменяць толькі правераным кодам з пераноснага файла; усе іншыя ключы выключаны. |

Для радкоў `migration_log` з не-NULL `session_id` правяраць адпаведнасць ужо існай, імпартаванай завершанай **або staged незавершанай** сесіі. Радкі незавершанай сесіі не ўстаўляць у звычайны `migration_log` да яе актывацыі; прымяняць тыя ж правілы дубляў і канфліктаў у каранціннай табліцы. Запісы `session_id IS NULL` параўноўваць па такім жа поўным ключы, а не адкідаць. Усе дублі ўнутры аднаго файла праходзяць гэтую ж праверку. Дадаўная табліца ў зоне B для ўжытых `snapshotId` ідэмпатэнтная: паўтор таго ж snapshot — no-op; запіс ключа і даных — **адна транзакцыя**.

### 4.3. Незавершаныя сесіі без змены існай схемы

`session.state` дазваляе толькі `active`, `paused`, `finished`, а індэкс `one_live_session` не дае другой жывой сесіі. Таму не ўводзіць чацвёртага значэння і не перабудоўваць `session`. Прапанаваны `restore_pending_session` — **новая асобная табліца зоны B** (дабаўная міграцыя; `session_id` як PK), дзе ўвесь зыходны прагрэс незавершанай прагулкі чакае ручнога выбару.

**Звязаныя запісы захоўваць разам:** дадаць `restore_pending_guide_hint_state` і `restore_pending_migration_log` для child-радкоў незавершаных сесій. Абедзве табліцы прывязаныя да `restore_pending_session.session_id`; захоўваць паказ/адхіленне падказак, факты міграцый і іх зыходныя значэнні, не змяняючы іх. Радкі для `session_id IS NULL` не прывязаныя да незавершанай сесіі і застаюцца ў асноўным `migration_log`. Імпарт бацькоўскага і ўсіх яго даччыных запісаў — адна транзакцыя; частковае аднаўленне забаронена.

Гэтыя табліцы не ўдзельнічаюць у `getLiveSession`; імпарт не запускае GPS, аўдыё або сетку. Пасля завяршэння імпарту наступны экспарт павінен уключаць **і** звычайныя завершаныя сесіі, **і** адкладзеных кандыдатаў з іх даччынымі запісамі (§3), інакш паўторны backup страціць яшчэ не працягнутую прагулку. Пры супадзенні `session_id` з іншымі данымі адмовіць імпарту без перазапісу. Толькі па выразным дзеянні карыстальніка, пры адсутнасці іншай жывой сесіі, праверыць даступнасць гіда і ў **адной транзакцыі** перанесці кандыдата ў `session` са станам `paused`, яго `restore_pending_guide_hint_state` у `guide_hint_state`, а `restore_pending_migration_log` у `migration_log` з тымі ж правіламі канфліктаў, пасля чаго выдаліць staged радкі. Адкат пры любой памылцы; ніводная ўжо адхіленая падказка не можа зноў паказацца толькі праз перанос. Пры адсутнасці файлаў пакінуць кандыдата без запуску; `readinessFor` вызначае гатоўнасць па сапраўдных файлах, а не па backup.

## 5. Android правілы

Генератар — новы config plugin у `tools/android-build/`, выкліканы ў `app.json` па прыкладзе існых `with-playback-only.cjs` і `with-shape-aware-icons.cjs`. Ён задае абедзве спасылкі на Android XML у выніковым release manifest.

- **API 24–30:** `android:fullBackupContent` з адзіным `<include domain="file" path="kudy-portable/progress.v1.json" requireFlags="clientSideEncryption"/>`. Спецыяльныя правілы для legacy D2D і адсутнасці магчымасці шыфравання — кансерватыўная адмова, пакуль не даказана на прыладзе.
- **API 31+:** `android:dataExtractionRules`. `<cloud-backup disableIfNoEncryptionCapabilities="true">` і `<device-transfer>` маюць кожная **свой** `<include domain="file" path="kudy-portable/progress.v1.json"/>`. Не спадзявацца на прапушчаную секцыю як на забарону.
- **Забарона:** ніякіх шырокіх `include` для `file`, `database`, `sharedpref`, `root`, `external` або device-protected даменаў. Выключыць `files/SQLite/` з `-wal`/`-shm`, `files/bundles/` і `SecureStore` у кожным рэжыме; у тэстах правяраць выніковыя XML, а не толькі зыходны код plugin.
- Фактычны `files/SQLite/` шлях пацвярджаецца [APR-09](APR-09-android-backup.md) для ўсталяванага Expo SQLite, але перад прыёмкай праверыць фізічную прыладу і свежую `processReleaseMainManifest`.

## 6. Абавязковы небяспечны пераход: копія да новай палітыкі

Ранейшы агульны Android backup **можа** аднавіць увесь `kudy.db` перад першым запускам новай версіі. Нельга спачатку выклікаць `ensureDeviceIdentity`, а потым чысціць старыя даныя. Патрэбны pre-bootstrap каранцін з доказам, што ён распазнае **restore** без ілжывай ачысткі звычайнага **upgrade** (абодва могуць упершыню сустрэць новы marker). Адна толькі адсутнасць новага `no_backup` marker — **не дастатковы сігнал**. Няма дазволу сціраць гісторыю або сеткавыя чэргі з сапраўднай зыходнай устаноўкі.

**Рашэнні, якія нельга прымаць замест уладальніка:** пацвердзіць дапушчальную страту апошніх незахаваных у OS backup змяненняў (прамежак паміж SQLite commit, snapshot і OS transport) альбо выбраць і праверыць натыўны `BackupAgent`; асобна ўзгадніць, што legacy D2D без гарантаванага шыфравання можа не пераносіць прагрэс. Пакуль рашэнні адсутнічаюць, гэтыя выпадкі — **не прынятыя** trade-off і release blockers, а не «асобныя асаблівасці» без наступстваў.

Гэта **адкрыты тэхнічны gate**, а не пацверджанае рашэнне. Патрэбны асобны ізаляваны тэст старой копіі і апісанне таго, як адрозніць upgrade ад restore; без яго нельга назваць рэалізацыю бяспечнай ці ўключыць backup у рэлізе.

## 7. Пацверджанне да зліцця

1. Node + рэальны SQLite: экспарт/імпарт усіх дазволеных калонак, адмоўныя выпадкі для забароненых табліц і ключоў, несапраўдныя тыпы, паўтор і restart. Асобна праверыць, што **адхілены або адкладзены snapshot не губляецца пры наступным экспарце**, што сапсаваны лакальны `ui_locale` не перамагае валіднае адноўленае значэнне, і што staged дзіцячыя радкі даходзяць да звычайнай `session` у той жа транзакцыі, і што паўторны экспарт захоўвае яшчэ не актываваную pending-прагулку.
2. Праверка plugin на сапраўднай Expo-мадэлі згенераваных XML + выніковага manifest. Змяненне кожнага XML `include`, спасылкі manifest або выключэнне plugin павінна рабіць тэст чырвоным.
3. `npm run typecheck`, `npm test`, `npm run arch:check`, `npx --yes jscpd@5.1.2 --config .jscpd.json --no-tips .`; Showboat з `uvx showboat==0.6.1 verify`.
4. Ізаляваныя Android legacy/12+ cloud і D2D: backup, reinstall, new device, update без выдалення, offline, device-delete, старая копія да новай палітыкі. Зняць non-secret параўнанні і SHA артэфактаў. Калі прылада/транспарт недаступныя — `not-run`, **не** `pass`.
5. Да гэтых доказаў GP-14 застаецца адкрытым; production device, асабісты акаўнт і `bmgr wipe` не выкарыстоўваць.

## 8. Стан гэтага этапу

- Пацверджаны з кода дазволеныя і забароненыя вобласці, кананічныя ўладальнікі даных і прапанаваны фармат.
- **Не рэалізавана:** runtime export/import, plugin, міграцыі, тэсты, release manifest, Android restore і Showboat.
- **Удакладнена пасля рэв'ю:** асобныя табліцы для неактыўных прагулак і іх дзіцячых запісаў, каранцін адхіленага/адкладзенага файла, моманты экспарту, маркер паходжання, правілы канфліктаў і параўнанне з `BackupAgent`. Усё гэта пакуль **праект дызайну**, не рэалізацыя.
- **Не вырашана:** бяспечнае адрозненне pre-policy OS restore ад звычайнага in-place upgrade без пераноснага файла і атамарнасць запісу Expo FileSystem. Да пацверджання гэтых межаў backup у рэлізе забаронены.
