# KUDY — дадзеныя і монетызацыя

Гэты файл апісвае дадзеныя і пакупкі першай аўдыёпрагулкі. Горад — агульны кантэкст і для будучых рубрык (`01`); іх схему і платнасць вызначаем у тэхнічным спецыфікаванні, не маскіруем артыкулы пад RouteStop.

## Гарады і краіны

- **City** — цэнтральная адзінка кантэнту. Кожны Place / Story / Route / Recommendation мае `city_id` ужо ў MVP, нават калі UI паказвае толькі Гданьск.
- **Country** — не асобная табліца зараз, дастаткова поля `country_code` на City. Пры адной актыўнай краіне асобная сутнасць з FK і міграцыямі — залішняя нармалізацыя; лёгка нарасціць да табліцы пазней, калі гарадоў/краін стане больш за некалькі.
- **UI:** пераключальнік горада не паказваецца ў MVP. Пазней — аўтаматычнае вызначэнне горада па GPS ("Вы ў Гданьску") замест ручнога выбару; API/схема ўжо гатовыя, перарабляць нічога не трэба.

## Device / Identity / Entitlement

Entitlement (тое, што куплена) — асобнае паняцце ад Identity (тое, як чалавек аўтэнтыфікаваны). Але ў MVP уласнай Identity і `User` яшчэ няма: кожная ўстаноўка атрымлівае выпадковы `device_id`, які адначасова выкарыстоўваецца як RevenueCat App User ID.

```
MVP: device_id → RevenueCat customer → Entitlements
Phase 2: verified Apple/Google identity → User → некалькі device_id
```

RevenueCat застаецца крыніцай праўды пра пакупкі. Наш сервер не прымае сцяг «куплена» ад кліента і не чакае webhook: пры выдачы доступу ён сам запытвае актуальныя правы ў RevenueCat. Webhook апцыянальны і выкарыстоўваецца толькі для бухгалтэрыі і аналітыкі.

У Phase 2 з'явяцца `User`, правераная Apple/Google identity і `/v1/link`. Толькі тады магчымыя перанос пакупак паміж iOS і Android, а таксама прагрэс, які перажывае пераўстаноўку. Да праверкі identity-токена гэты endpoint не існуе.

## Пакупкі — абстракцыя провайдара

```
Purchase → Provider: Apple | Google | Web
```

Не хардкодзіць `Purchase = ApplePurchase`. Каштуе амаль нічога зрабіць enum'ам адразу; эканоміць пераробку, калі пазней з'явіцца web-checkout.

## Тып entitlement — таксама enum

```
entitlement.type: ROUTE | ROUTE_EXTENSION | CITY_PASS | SUBSCRIPTION
```

MVP прадае `ROUTE` і `ROUTE_EXTENSION`; `CITY_PASS`/`SUBSCRIPTION` — у схеме, не ў продажы. Цэны — адкрытае пытанне, гл. `04_scope_and_roadmap.md`.

**Прадавацца можа маршрут цалкам або пашырэнне.** Наратыў двухузроўневы: `narration.tier = base | extended` (базавы і дадатковы матэрыял; узровень цікавасці не вызначае цану). Адсюль два правілы: бандл пласцісты (extended дадаецца пасля пакупкі без перазагрузкі маршруту), і падпісаныя URL выдаюцца **па пласце** — інакш платнае аўдыё відно ў манifest бясплатнага.

**Доступ і загрузка:** замкнёныя кропкі маюць публічныя месцы/назвы/анонсы, але не поўныя тэксты або медыя. `/grant` выдае толькі файлы з маніфеста дазволенага маршруту, версіі, мовы і пласта (`09`, разд. 5). Кропкі адкрываюцца пасля поўнай праверанай загрузкі; версія актыўнай сесіі не мяняецца. Купля маршруту не азначае адключэнне магчымай будучай рэкламы; асобны прадукт без рэкламы яшчэ не вырашаны.

## IAP і плацежныя правілы плятформаў

Гэта не толькі UX-выбар, а патрабаванні App Store / Google Play:

- Apple і Google патрабуюць IAP для лічбавага кантэнту, які спажываецца ўнутры дадатку (Apple Guideline 3.1.1), плюс абавязковы механізм "Restore Purchases".
- У ЕС (значыць, і Польшча/Гданьск) дзейнічае DMA: паводле стану на 2026 і Apple, і Google дазваляюць альтэрнатыўныя плацяжы/знешнія лінкі ў EEA. У Google гэта ўжо канкрэтная праграма (alternative billing EEA), з 30.06.2026 service fee аддзелены ад billing fee, базавая стаўка сэрвіснага збору — ад 10% на першы $1M выручкі ў год. Дэталі і стаўкі мяняюцца — правяраць актуальныя ўмовы перад рашэннем.
- Для аднаго горада і пачатковай стадыі дадатковая складанасць (рэгіянальная логіка, уласны GDPR-контур для плацяжоў, асобны checkout) не акупляецца.

**Рашэнне:** старт — звычайны Apple/Google IAP без выключэнняў. DMA/альтэрнатыўны білінг — опцыя на потым, калі аб'ём выручкі апраўдае складанасць; дзякуючы Provider-абстракцыі вышэй, пераход не патрабуе перапісваць схему.

## Entitlement flow без акаўнта

1. Пры першым запуску сервер стварае выпадковыя `device_id` і `device_secret`; RevenueCat SDK канфігуруецца з гэтым `device_id`.
2. `ROUTE` і `ROUTE_EXTENSION` прадаюцца як **non-consumable one-time purchases**. Пасля пакупкі кліент просіць `/v1/grant`, а сервер сам чытае entitlement праз RevenueCat REST API.
3. На новай прыладзе ў **той самай краме** карыстальнік запускае `restorePurchases()`; пакупка аднаўляецца праз той самы Apple ID або Google-акаўнт паводле RevenueCat Restore Behavior `Transfer to new App User ID`.
4. Перанос iPhone → Android без уласнага акаўнта немагчымы і вынесены ў Phase 2 разам з `/v1/link`.

## Зрабіць адразу (бясплатна цяпер, дорага потым)

- `city_id` + `country_code` на ўсім кантэнце
- Entitlement асобна ад Identity; RevenueCat — крыніца праўды, сервер правярае права сам
- `Purchase.provider` як enum
- `entitlement.type` як enum
- стабільны `RouteStop.id`; `position` — толькі парадак, не ідэнтычнасць і не ключ прагрэсу

## Не рабіць пакуль

- Асобная Country-табліца
- Provider = Web checkout — рэальная рэалізацыя
- Subscription / City Pass — бізнес-логіка і цэны
- Weather / sunset / opening-hours context engine для Moments
- Любыя "мяккія" здагадкі пра стан або настрой чалавека

## Падборкі і водгукі — пашырэнне 2026-09-13

Статычны публічны discovery-index змяшчае ўласныя месцы, падборкі і прэв'ю гідаў. Collection мае толькі спасылкі; не новы entitlement або Run. Для непублічных ацэнак дадаюцца аўтарызаваныя feedback endpoints і прыватныя табліцы з RLS, прывязаныя да існуючай устаноўкі, без новага User-акаўнта. Водгукі не захоўваюцца ў route-бандлах. Схемы, выдаленне, даступнасць моў і давер — [21](architecture/21_discovery_feedback_architecture.md). Аўтарскія пазнакі часу/сезону не з'яўляюцца забароненым вышэй context engine.
